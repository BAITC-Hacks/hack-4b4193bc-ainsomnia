# ТЗ: модель риска просрочки обращения 109

## Контекст

Данные единого контакт-центра 109, Карагандинская область: 143 954 строки, 2022–2023 гг.
Поля статуса и даты закрытия в данных **нет**. Целевую переменную конструируем сами.

Задача: по метаданным, известным **в момент поступления** обращения, предсказать
вероятность того, что его обработка превысит нормативный срок.

Файл: `Обращения_граждан_109_-_Карагандинская_область.csv`

Колонки: `created_date, updated_date, submission_date, appeal_type, source, region,
district, appeal_address, category, sub_category, executor_gov_org, answer_type, type`

Формат дат: `%m/%d/%y %H:%M`

---

## Стек

Python 3, pandas, scikit-learn. Модель — `HistGradientBoostingClassifier`
(есть в sklearn, поддерживает категориальные признаки нативно, внешних
зависимостей не требует). Никакого PyTorch, никаких трансформеров — текста в
данных нет.

---

## Шаг 1. Загрузка и чистка

1. Загрузить CSV, распарсить `created_date` и `updated_date`.
2. В файле есть **битые строки из-за незакрытых кавычек** — примерно 400 штук, у
   них значения съехали по колонкам (в `answer_type` и `type` попадают куски
   названий организаций). Отфильтровать: оставить только строки, где
   `appeal_type` входит в `{'Запрос информации', 'Обращение', 'Инцидент'}`.
   **Вывести в консоль, сколько строк выброшено.**
3. Проверить и вывести: число строк до и после, доля пропусков по каждой колонке.

## Шаг 2. Целевая переменная

```
days = (updated_date - created_date) в сутках
```

Оставить только `appeal_type in ('Обращение', 'Инцидент')` — «Запрос информации»
это справочная, она закрывается в ту же минуту и в задачу не входит.
Ожидаемый размер выборки: ~62 200 строк.

```
y = 1, если days > 15, иначе 0
```

**Вывести:** размер выборки, долю `y=1` в процентах, распределение `days` по
квантилям (50/75/90/95/99).

## Шаг 3. Признаки

Использовать **только то, что известно в момент поступления обращения**:

| Признак | Тип |
|---|---|
| `appeal_type` | категориальный |
| `source` | категориальный |
| `district` | категориальный |
| `category` | категориальный |
| `sub_category` | категориальный |
| `executor_gov_org` | категориальный |
| `type` | категориальный |
| `hour` из created_date | числовой |
| `dayofweek` из created_date | числовой |
| `month` из created_date | числовой |
| `has_address` — заполнен ли `appeal_address` | бинарный |
| `executor_load_7d` | числовой |
| `district_load_7d` | числовой |

`executor_load_7d` — сколько обращений к этому же `executor_gov_org` было
создано за предыдущие 7 суток до момента поступления текущего.
`district_load_7d` — то же самое по району.

**Критично:** обе фичи считаются только по прошлому. Никакого заглядывания
вперёд, никаких оконных функций, захватывающих будущие строки. Отсортировать по
`created_date` и считать причинно.

### Что запрещено использовать как признак

- `updated_date` и `days` — из них построен таргет, это прямая утечка
- `submission_date` — проверить, отличается ли она от `created_date`; если
  совпадает почти всегда, выбросить
- `region` — константа внутри одного региона
- `answer_type` — **под вопросом.** Обучить две версии модели: без него и с ним.
  Вывести обе метрики отдельно. Если с ним качество прыгает заметно — значит,
  поле проставляется после обработки, и это утечка.

## Шаг 4. Разбиение

**Разбиение строго по времени, не случайное.**

```
train: created_date <  2023-07-01
test:  created_date >= 2023-07-01
```

Причина: модель будет работать на будущих обращениях, значит и проверять её надо
на будущих. Случайный сплит завысит качество.

**Вывести:** размер train и test, долю `y=1` отдельно в train и отдельно в test.
Доли будут отличаться — это ожидаемо, в 2022 просрочек 27%, в 2023 уже 42%.

Все преобразования (кодирование категорий, заполнение пропусков) обучать
**только на train** и затем применять к test. Не считать статистики по всему
датасету до разбиения.

## Шаг 5. Модели

Обучить три штуки и сравнить на одном и том же тесте:

1. **Пустышка** — `DummyClassifier(strategy='most_frequent')`. Всегда отвечает
   самым частым классом. Это нижняя планка.
2. **Логрег** — `LogisticRegression` на one-hot кодировании, с
   `class_weight='balanced'`.
3. **Бустинг** — `HistGradientBoostingClassifier` с `categorical_features`.

## Шаг 6. Метрики — вывести всё это в консоль

Для каждой из трёх моделей:

- accuracy
- ROC-AUC
- PR-AUC (average precision)
- precision, recall, f1 **для класса 1 отдельно**
- матрица ошибок в виде таблицы с подписями (TN / FP / FN / TP)
- полный `classification_report`

Дополнительно только для бустинга:

- **permutation importance**, топ-15 признаков, посчитанная на тесте
- **таблица калибровки:** разбить предсказанные вероятности на 10 децилей и
  для каждого вывести: границы децили, число объектов, среднюю предсказанную
  вероятность, фактическую долю просрочек. Если модель откалибрована, две
  последние колонки должны идти рядом.

## Шаг 7. Артефакты

```

```

Плюс единый скрипт `train.py`, который прогоняется от начала до конца одной
командой и печатает весь отчёт. Никаких ноутбуков с ручным порядком ячеек —
результаты должны воспроизводиться.
