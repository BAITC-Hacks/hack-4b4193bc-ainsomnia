# NAZAR-109 — правила проекта

Модель риска просрочки обращений в единый контакт-центр 109 + детектор всплесков.
Данные: 12 файлов, 7 регионов Казахстана, **шесть** семейств схем, **1 063 216** строк.
Горизонт работ — октябрь.

## 0. Развёртывание с нуля

Всё, что нужно постороннему инженеру, чтобы получить работающую витрину. Шаги строго по порядку: каждый следующий читает то, что записал предыдущий.

**Требуется:** macOS или Linux, Python 3.12, `uv` (или любой способ создать venv). Для PDF-выгрузки на Linux — пакет шрифтов DejaVu (см. ограничение в 5i); Excel-выгрузка шрифтов не требует.

**Место на диске — две разные цифры, ставить нужно не всё сразу:**

| Что | Файл зависимостей | Место |
|---|---|---|
| Витрина, детектор, прогноз, NLQ, демо-сценарий | `requirements.txt` | **~2 ГБ** |
| Дообучение классификатора тем (раздел 5k) | `requirements-ml.txt` | **дополнительно ~3 ГБ** (torch, transformers) плюс кэш моделей в `~/.cache/huggingface` |

`requirements-ml.txt` вынесен отдельно намеренно: витрине torch не нужен, и тянуть три гигабайта ради неё нельзя. Всё из таблицы шагов ниже работает без него.

```bash
# 1. Репозиторий
git clone <repo> NAZAR-109 && cd NAZAR-109

# 2. Окружение и сам проект — одной установкой: зависимости из requirements.txt,
#    пакет src (режим -e: код остаётся в репозитории) и две команды в .venv/bin —
#    nazar-build-data и nazar-dashboard. Они работают из любого каталога; команды
#    вида `python -m src...` ниже по-прежнему запускаются ИЗ КОРНЯ репозитория:
#    пути в коде относительные (data/, reports/).
uv venv .venv
uv pip install --python .venv/bin/python -e .

# 3. Сырые данные — в репозитории их НЕТ и не будет: они содержат ПДн (раздел 1).
#    Получить у владельца данных и положить в каталог в корне репозитория:
#        drive-download-20260907T161509Z-1-001/
#    Ожидается 12 файлов: 8 CSV и 4 XLSX по семи регионам. На верхнем уровне 11 записей:
#    Павлодар — подкаталог «Обращения граждан Павлодар» с двумя частями; имя
#    подкаталога и обоих файлов зашито в src/adapters/adapters.py.
#    Каталог под .gitignore, имя каталога зашито в src/adapters/adapters.py.

# 4–7. Сборка данных — одна команда: адаптеры -> сводная таблица -> темы ->
#      проверка покрытия, строго по порядку; на первой ошибке останавливается.
.venv/bin/nazar-build-data

# 8. Витрина — одна команда.
.venv/bin/nazar-dashboard                          # аргументы streamlit передаются дальше
```

Проверено: живая витрина, запущенная `nazar-dashboard` из `/tmp` без `PYTHONPATH`, открыта безголовым Chrome и отрисовала все восемь блоков без ошибок. **Оговорка:** пакет называется `src` — это имя верхнего уровня, и в общем окружении с другим проектом того же устройства они бы столкнулись. В отдельном `.venv` и в контейнере столкновения нет; переименование в `nazar` — в долг, раздел 9, не трогать до защиты.

**Контрольные числа после сборки данных (шаг 6)** — если не сходятся, дальше идти нельзя: `data/unified.parquet` = **988 776** строк; по классам `problem` 658 103, `info` 308 305, `system` 22 368; по регионам Павлодар 666 634, Караганда 143 311, ВКО 83 382, Туркестан 52 050, Костанай 20 591, Алматы 19 334, Акмола 3 474.

## 0b. Готовность к внедрению (оценка 2026-09-25)

Честный список. «Сделано» значит проверено прогоном, а не написано.

1. **Развёртывание — СДЕЛАНО на macOS; Linux и Windows не проверены.** Установка — одна команда (`uv pip install -e .`), сборка данных — одна (`nazar-build-data`), витрина — одна (`nazar-dashboard`); обе команды работают из любого каталога. Проверено на чистой копии — ровно те файлы, что уходят в git, новое окружение: установка 8 с; сборка данных — таблица совпала с эталоном раздела 0; `train.py` — `metrics.json` совпал байт в байт; живая витрина открыта безголовым Chrome — все восемь блоков, ошибок нет. **Не сделано:** прогон раздела 0 на чистой Linux-машине и на Windows. `uv` — внешний инструмент; обычные `python -m venv` и `pip install -e .` должны работать так же, но не проверялись.

2. **Воспроизводимость — СДЕЛАНО ЧАСТИЧНО.** Сделано: прямые зависимости закреплены точными версиями (`requirements.txt`, 11 пакетов), Python 3.12 задан в `pyproject.toml`; сборка данных детерминирована — повторная сборка 2026-09-25 дала таблицу, совпадающую с прежней ячейка в ячейку; `train.py` воспроизвёл `metrics.json` байт в байт; отчёты прогноза и NLQ — байт в байт (2026-09-13). **Не сделано:** (а) **транзитивные зависимости не закреплены** — установка разрешает 51 пакет, закреплены 11, через полгода `pip` может поставить другие версии; нужен lock-файл (`uv pip compile requirements.txt -o requirements.lock`) и установка из него; (б) **версия сырой выгрузки не фиксируется** — нужен манифест файлов (имя, размер, sha256), который `nazar-build-data` сверяет перед сборкой; (в) дообучение на MPS воспроизводится только в пределах измеренного шума (5k).

3. **Тесты — СДЕЛАНО ЧАСТИЧНО.** Есть: регресс-тест разметки тем (шаг 4 сборки), прогон NLQ по 20 зафиксированным вопросам, числовые санити-чеки внутри `train.py`, самопроверки демо-сценария, проверка готовой выгрузки на ПДн. **Не сделано:** (а) **все тесты работают только на реальных данных с ПДн** — на машине без данных и в CI не запускается ничего; нужен маленький синтетический набор без ПДн в `tests/`; (б) проверки витрины — эмуляция запуска streamlit, пять сценариев отказа, сверка шапки с лентой, живой рендер в Chrome — написаны и прогнаны, но лежат в `analysis/ui/` вне git; их нужно перенести в `tests/` под pytest; (в) CI нет; (г) регресс-тест тем падает на любой новой выгрузке — см. пункт 7.

4. **Обработка ошибок — СДЕЛАНО для отсутствующих файлов и сборки PDF**, таблица выше. **Не сделано:** (а) ошибки на неожиданных данных — новый формат даты, новая или переименованная колонка — остаются трейсбеками; явно падают только адаптеры при доле непарсящихся дат выше 1%; (б) streamlit по умолчанию показывает трейсбек прямо в браузере — перед внешним показом выключить в `.streamlit/config.toml` (`client.showErrorDetails`); (в) сетевые ошибки загрузки моделей Hugging Face (5k, 5l) не обрабатываются.

5. **Контейнер — ФАЙЛЫ НАПИСАНЫ, НЕ ПРОВЕРЕНЫ: Docker на этой машине не установлен.** `Dockerfile`, `docker-compose.yml`, `.dockerignore`; данные и построчные файлы подключаются томами и в образ не попадают. Инструкция — раздел «Контейнер» ниже. **Нужно:** `docker compose build` и `docker compose up` на машине с Docker, затем отдельно — сборка PDF в контейнере: Chromium для графиков установлен в образ, но запуск kaleido в нём не проверен.

6. **Журналирование — НЕ СДЕЛАНО.** Сейчас команды печатают в stdout/stderr, у streamlit свой журнал по умолчанию. Нет журнала действий пользователей (кто открыл, какие фильтры, что выгрузил), нет уровней, ротации и сбора в одно место. **Нужно:** `logging` с уровнями во всех командах; журнал выгрузок — кто, когда, какие фильтры, сколько строк. «Кто» без входа в систему записать нельзя — см. пункт 8. В контейнере журнал идёт в stdout для сборщика логов заказчика.

7. **Обновление данных по расписанию — НЕ СДЕЛАНО.** Данные — разовая выгрузка, получена вручную. `nazar-build-data` пересобирает всё с нуля за полминуты, но для регулярной работы это не готово:
   - **на новой выгрузке сборка остановится на шаге 4:** регресс-тест тем сравнивает число строк в каждой теме с эталоном текущей выгрузки и падает при любом изменении. Для регулярной сборки нужна другая проверка — доля «прочего» по регионам и переезды категорий между темами, а не абсолютные числа;
   - адаптеры сверяют число строк с инвентарём текущей выгрузки; на новой они печатают «РАСХОЖДЕНИЕ», сборку не роняют, но шумят. Имя каталога выгрузки зашито в код;
   - нет источника: нужен регулярный канал от заказчика — выгрузка из базы, SFTP или API — и договорённость о формате (раздел 10, находка о кавычках);
   - нет расписания (cron, systemd timer или планировщик заказчика), нет пересчёта детектора и прогноза после сборки, нет оповещения о сбое.

   Модель риска на новых данных переобучается осознанно, не по расписанию: порог 15 суток и выбор модели — решения основной сессии (раздел 2).

8. **Роли и разграничение доступа — НЕ СДЕЛАНО.** Витрина без входа: любой, кто знает адрес, видит все регионы и может выгрузить Excel и PDF. **Нужно:** вход через единую учётную запись заказчика (в streamlit есть встроенный вход по OIDC — `st.login`, либо обратный прокси с авторизацией), роли (например: руководитель — просмотр; аналитик — выгрузка; инженер — сборка данных), ограничение регионов по роли, журнал (пункт 6). **До этого витрину поднимать только во внутренней сети** — в `docker-compose.yml` порт по умолчанию открыт только на `127.0.0.1`.

9. **Работа с персональными данными — СДЕЛАНО в границах проекта, НЕ СДЕЛАНО на уровне эксплуатации.** Сделано: колонки ПДн и свободный текст в канон не попадают (разделы 1, 5c); строки со сдвигом полей, через которые ПДн просачивались, отсеиваются; готовая выгрузка проверяется на ПДн (0 нарушений); сырьё, таблицы, модели и построчные файлы — вне git (`.gitignore`) и вне образа (`.dockerignore`); примеры печатаются только маскированными. **Не сделано:** (а) гарантии по свободному тексту нет — ФИО и адреса без цифр шаблонами не ловятся (5c); (б) сырые выгрузки и `data/` лежат на диске незашифрованными; (в) нет регламента хранения и удаления, нет журнала доступа; (г) нет оценки по Закону РК «О персональных данных и их защите»: кто оператор, на каком основании обработка, где данные хранятся. **Нужно:** решение заказчика и юриста по (в) и (г), хранение данных на стороне заказчика, шифрование тома с данными, журнал доступа (пункт 8).

### Препятствия к внедрению — и что нужно, чтобы их снять

Три вывода из оценки выше, которые блокируют регулярную эксплуатацию, а не просто остаются недоделками.

1. **Регресс-тест тем блокирует любую новую выгрузку.** `tests/test_topic_coverage.py` сравнивает число строк в каждой теме с эталоном текущей выгрузки (`tests/topic_coverage_baseline.json`) и падает при любом изменении. Это правильно для правок маппинга на неизменных данных, но на новой выгрузке числа меняются всегда, и `nazar-build-data` остановится на шаге 4. **Для снятия нужна проверка другого рода** — не абсолютных чисел, а свойств разметки:
   - доля «прочего» внутри `problem` по каждому региону не выше порога — цель «меньше 15%» из 5e;
   - у категорий, которые уже были в эталоне, тема не сменилась — сравнение сопоставления «категория → тема» целиком. Это ловит и переезды между темами, и симметричный обмен, который нынешний тест пропускает (раздел 9);
   - новые категории не роняют сборку, а выводятся списком для ручного просмотра.

   Нынешний тест остаётся для правок `src/topic_mapping.py`; в регулярную сборку идёт новая проверка.

2. **Все тесты требуют реальных данных с ПДн — CI невозможен.** На машине без выгрузки не запускается ни один тест, а выгрузку в CI класть нельзя (раздел 1). **Для снятия нужен синтетический набор без ПДн** в `tests/`:
   - по несколько сотен строк на каждое из шести семейств схем, с теми же колонками и форматами дат;
   - с известными ловушками: сдвиг полей на кавычках, дубли по ключу, провал выгрузки как у Туркестана, первый месяц ряда;
   - генерируется скриптом и коммитится; на нём — pytest и CI.

## 2. Делегирование

### Маршрутизация

| Тип запроса | Агент | Модель |
|---|---|---|
| «Сколько строк / колонок / пропусков / уникальных значений в файле X» | `data-recon` | haiku |
| «Какое временное окно у файла X», «какой формат дат», «сколько не парсится» | `data-recon` | haiku |
| «Распределение колонки A в разрезе колонки B», «сколько дублей по ключу» | `data-recon` | haiku |
| «Сравни два региона по одному измерению» | `data-recon` | haiku |
| «Приведи семейство схем к канону», «восстанови заголовки xlsx» | `schema-adapter` | sonnet |
| «Сверь числа в отчётах с metrics.json», «проверь артефакты перед демо» | `artifact-auditor` | haiku |

Модель выбрана по цене ошибки, не по объёму работы. Ошибка `data-recon` видна сразу при сверке с известным числом — haiku. Ошибка `schema-adapter` проявится позже и потянет за собой модель — sonnet.

### Не делегируется никогда

Ошибка в этих решениях не видна из результата — она проявится поздно и дорого. Они остаются в основной сессии:

- выбор целевой переменной и порога SLA
- состав признаков, включая решение, что считать утечкой
- логика разбиения train/test
- интерпретация метрик и вердикт «модель годится / не годится»
- решение объединять ли регионы

Отдельно отвергнуты как агенты: `report-formatter` (передача уже посчитанных чисел через ещё одну модель добавляет риск описки там, где она дороже всего), `metrics-interpreter` и `leakage-auditor` (подпадают под запрет выше), `spike-detector` (выбор базовой линии и порога — модельное решение), `researcher` (дублирует встроенный `Explore`), `test-writer` (проверка здесь — числовые санити-чеки внутри `train.py`, не юнит-сьют).

### Правило проверки результата

**Результат субагента сверяется с уже известными числами, а не принимается на веру.**

1. Любое число от агента, пересекающееся с эталонной таблицей (раздел 4), сверяется с ней до использования.
2. Если агент вернул число без знаменателя («7.8%») — вернуть на пересчёт с абсолютными величинами.
3. Если агент вернул вывод или рекомендацию вместо чисел — вывод игнорируется, берутся только числа.
4. Расхождение агента с эталоном — это повод перепроверить **оба** числа, а не переписать эталон под агента.
5. Новое число, которое войдёт во внешний отчёт, предварительно проходит через `artifact-auditor`.

## 3. Открытые вопросы

### ОТКРЫТО: разброс доли нарушений SLA в 4,677 раза — блокирует объединение регионов

Костанай и Туркестан имеют практически идентичную схему, но дают `slabreach=True` **34,9%** против **7,5%** — разброс в **4,677 раза**. Это не шум.

*Поправка 2026-09-13:* раньше здесь стояло «4,6 раза» — округление 4,677 в меньшую сторону. Точные доли 34,899% (7 186 из 20 591) и 7,462% (3 884 из 52 050).

**Объединять регионы в одну ОБУЧАЕМУЮ МОДЕЛЬ до объяснения запрещено.** Запрет снимается только явным решением в основной сессии, после того как расхождение объяснено.

**Уточнение области запрета (2026-09-09).** Запрет касается обучения общей модели, а не сводных таблиц. Собрать `data/unified.parquet` с колонкой источника для модуля 3 — **разрешено и сделано**: дашборд не переносит разметку SLA между регионами, поэтому расхождение 34,9%/7,5% на него не влияет. `schema-adapter` при первом заходе прочитал запрет расширительно и отказался собирать таблицу — формально верная эскалация, решение принято в основной сессии.

Гипотезы к проверке через `data-recon` — агент возвращает числа, вывод делается в основной сессии:

1. Различаются ли значения `sla` по одинаковым категориям между регионами.
2. Различается ли структура категорий (`servicelevel1/2/3`, `category`).
3. Различается ли доля закрытых обращений и состав `status`.

Сопутствующие факты, требующие объяснения: в Туркестане дедуп по `incidentcode` снимает **46 826 строк из 98 876 — 47% файла** (в Костанае дублей ноль), и у Туркестана же в выгрузке нет обращений полгода (раздел 10, пункт 7).

### ОТКРЫТО: `updated_date` в Караганде — не дата закрытия

`updated_date` — дата последнего изменения записи. Запись 2022 года, к которой административно прикоснулись в 2025-м, даёт 600+ суток, и это не время обработки. Гипотеза требует подтверждения у владельца данных. Затронуто ~2% выборки (`days > 180`).

### ОТКРЫТО: порог 15 дней — догадка; проверен, но не обоснован

**Таргет в `train.py` построен по порогу 15 суток из ТЗ. Нормативы `sla` не применялись.**

Порог взят из ТЗ без обоснования и обоснованным не стал: проверка показала, почему его нельзя заменить, но не почему он верен. Разведка `sla` в Костанае и Туркестане проведена (`data-recon`), числа сверены независимым пересчётом — сошлись.

**Фактические нормативы — 1–7 дней, не 15:**

| | Костанай | Туркестан |
|---|---|---|
| `sla` = 7 | 12 288 (59.7%) | 31 243 (60.0%) |
| `sla` ≤ 7 | 20 315 (**98.7%**) | 51 971 (**99.8%**) |
| `sla` ≥ 14 | 276 (1.34%) | 79 (0.15%) |
| набор значений | 1,2,3,4,5,7,14,15,30 | те же + аномалии 0, 6, 1069 |

**Норматив — свойство под-услуги, и дисциплина разная по регионам.** Доля строк в группах с единственным значением `sla`: по `servicelevel1` — Костанай 20.0% (22 из 50 групп), Туркестан 1.5% (12 из 53); по `servicelevel2` — Костанай **69.2%** (212 из 228), Туркестан **15.1%** (190 из 277). Это материал к открытому вопросу о расхождении 34,9% / 7,5%.

**Почему порог не изменён: справочники несопоставимы.** `category` в Караганде — не таксономия услуг, а названия организаций-исполнителей плюс «Справочная» (44.78%). `sub_category` (665 значений) ближе по смыслу к `servicelevel2` (228 значений), но общего ключа нет, регистр и гранулярность разные, внутрь намешаны артефакты колл-центра («Сброс звонка», «Зачитывание ответа») и выборы. Перенос нормативов потребовал бы ручного словаря на ~600 значений — это догадка в виде данных, что запрещено разделом 1 и промптами агентов.

**Следствие:** 15 дней — не норматив, а консервативная граница примерно вдвое мягче фактической (7 суток для 60% обращений). Так и описывать, не выдавая 15 за норму.

**Вопрос остаётся открытым.** Закрыть его можно только нормативом от владельца данных по Караганде либо ручным словарём соответствия `sub_category` → `servicelevel2`. До этого порог остаётся допущением, а не фактом.

### Справочник как нижняя планка

Подробные числа — `reports/baseline_vs_model.md`.

Таблица долей просрочек по `sub_category`, посчитанная на train и применённая к test без обучения, даёт ROC-AUC 0.7485 и PR-AUC 0.6263. Основная модель — 0.7810 и 0.6836.

**Прирост над базой считать от PR-AUC.** База PR-AUC — фактическая доля класса 1 (0.4224), база ROC-AUC — гипотетическая монета (0.5). При несбалансированных классах вторая льстит справочнику.

| Метрика | База | Справочник | Модель | Справочник закрывает | Модель добавляет |
|---|---|---|---|---|---|
| **PR-AUC** (использовать эту) | 0.4224 — доля класса 1 | 0.6263 | 0.6836 | **78.1%** | **+28.1%** |
| ROC-AUC (справочно) | 0.5000 — случайное угадывание | 0.7485 | 0.7810 | 88.4% | +13.1% |

**Две последние колонки — разные отношения, они не складываются в 100%.** «Закрывает» = (справочник − база) / (модель − база) = 0.2039 / 0.2612. «Добавляет» = (модель − справочник) / (справочник − база) = 0.0573 / 0.2039. Читать их как части одного целого («78% плюс 28% — почти всё») нельзя.

### ИСПРАВЛЕНО: модель выигрывает у справочника во всех сопоставимых точках

Более ранняя формулировка «по recall справочник обходит модель» **была неверна** — recall сравнивался в разных рабочих точках (справочник на пороге 0.25, модель на 0.48). При сопоставимых порогах:

| Целевая точка | Подход | Precision | Recall |
|---|---|---|---|
| recall = 0.80 | справочник | 0.5786 | 0.8168 |
| recall = 0.80 | **модель** | **0.6123** | 0.8001 |
| precision = 0.65 | справочник | 0.6410 | 0.5116 |
| precision = 0.65 | **модель** | 0.6500 | **0.6757** |

При равной точности модель ловит на +0.1641 recall больше — **32% относительного прироста**. Это главный аргумент в пользу модели против справочника.

**Операционная таблица** (оператор проверяет топ по риску):

| Просмотр | Precision справочника | Precision модели | Охват справочником | Охват моделью | Потолок охвата |
|---|---|---|---|---|---|
| 10% | 0.6774 | **0.7628** | 0.1604 | **0.1806** | 0.2368 |
| 20% | 0.6759 | **0.7601** | 0.3201 | **0.3600** | 0.4736 |
| 30% | 0.6627 | **0.7075** | 0.4706 | **0.5025** | 0.7102 |

Потолок охвата — сколько просрочек физически помещается в долю: при 42.2% просрочек топ-10% не может содержать больше 23.7% всех. Модель берёт 76% от потолка, справочник 68%. Точность в топ-10% — 0.7628 против базовых 0.4224, рост в 1.81 раза.

**Гранулярность справочника.** На тесте он выдаёт всего **203** различных значения вероятности против 17 576 у модели (по неокруглённым вероятностям; в `reports/predictions.csv` вероятности округлены до 6 знаков — `out["y_prob"] = np.round(p_main, 6)` в `train.py`, — и по файлу различных значений 17 330): порог переключает подкатегорию целиком, рабочую точку под ёмкость оператора не подстроить. Это самостоятельный аргумент, независимый от метрик.

### ЗАКРЫТО: основная модель — логистическая регрессия, не бустинг

ТЗ назначало основной моделью `HistGradientBoostingClassifier`. Данные это не подтвердили: логрег 0.7810 против 0.7691 по ROC-AUC, 0.6836 против 0.6697 по PR-AUC, 0.6896 против 0.6712 по F1.

**Обоснование:** сигнал сосредоточен в высококардинальных категориальных признаках (`category` 308 значений, `sub_category` 665). Бустинг на них переобучается при сдвиге распределения — доля просрочек растёт с 32.2% в train до 42.2% в test, и выученные на train пороги по редким категориям на тесте не держатся. One-hot логрег с `min_frequency=20` схлопывает редкие уровни и переносится через сдвиг устойчивее.

### ЗАКРЫТО: четыре признака убраны

`executor_load_7d`, `district_load_7d`, `source`, `executor_gov_org` удалены. Метрики не просели, а выросли: ROC-AUC +0.0019, PR-AUC +0.0051, F1@порог +0.0067, recall 0.7420 → 0.7795.

Отдельно: в полной модели `executor_gov_org` имел заметную permutation importance (0.0445, третье место), но его удаление качество улучшило. Информация избыточна с `category`/`sub_category`, а привязка к конкретным названиям организаций мешает переносу на будущий период. Permutation importance измеряет опору модели, а не необходимость признака — различать.

Причинные load-признаки, самая трудоёмкая часть реализации, вклада не дали: `executor_load_7d` −0.00006, `district_load_7d` −0.00114.

**Известное ограничение: причинность load-признаков при одинаковой минуте.** `causal_load` упорядочивает строки с одинаковым `created_date` стабильной сортировкой, и строка, стоящая в CSV позже, учитывает соседку той же минуты как уже случившуюся. На выборке `train.py` (61 619 строк) завышенный счётчик получают 262 строки по `executor_load_7d` (0.43%) и 807 по `district_load_7d` (1.31%). Основную модель `logreg_trim` это не затрагивает — оба признака из неё убраны. Затронуты строки **«Логрег полный»** и **«Бустинг полный»** в таблице выше и permutation importance полной модели — на них опирались решения убрать признаки и отказаться от бустинга. Не исправляется, пока признаки не возвращаются в модель. `logic-auditor` оценил масштаб в 12 338 и 14 489 строк — это посчитано по всем 143 311 строкам Караганды, а не по обучающей выборке.

**Permutation importance основной модели:** `category` 0.1405, `sub_category` 0.0944, `appeal_type` 0.0218, `region` 0.0027, `district` 0.0014; остальные ≈ 0. Модель держится на том, о чём обращение.

**Калибровка.** Дециль 1: предсказано 0.0325, фактически 0.0603. Дециль 7: 0.6372 против 0.5175. Дециль 10: 0.9052 против 0.7627. Систематическая переоценка риска в середине и вверху — следствие сдвига train 32.2% → test 42.2%. Подгонкой под тест не правится. Вероятности использовать как ранжирование, не как абсолютный риск.

**`answer_type` утечкой не является:** 0.7889 против 0.7810, дельта +0.0079.

ROC-AUC 0.781 — красного флага утечки (>0.95) нет.

## 5f. Детектор всплесков (2026-09-11)

`src/spikes.py`. Запуск: `.venv/bin/python -m src.spikes [--k 4] [--min-count 10] [--window 28] [--season-tol 10] [--keep-first-month]`. Дневной ряд по срезу: `--series РЕГИОН ТЕМА С ПО`.

Дневные счётчики регион × тема, только `problem`, дни без обращений дозаполнены нулями. Скользящая медиана и MAD по окну 28 суток, **окно сдвинуто на `[t-28, t-1]`** — день всплеска в него не входит (подтверждено `logic-auditor` на ряде из 35 точек). Всплеск: `count > median + K·MAD` и `count >= 10`.

Две шкалы ранжирования: **кратность** = пик / max(медиана на старте, 1) и **прирост** = пик − медиана на старте. Первая выводит наверх скачки с нулевого фона, вторая — крупные события на высоком фоне.

**Первый календарный месяц ряда каждого региона выброшен целиком** — и как объект детекции, и из окон. Отсечено 39 всплесков: Караганда 12, Павлодар 11, Туркестан 6, Костанай 5, Акмола 2, Алматы 2, ВКО 1.

**Окно, задетое пропуском выгрузки, детекцию отключает (2026-09-13).** Пропуск — 7+ дней подряд без обращений **по региону целиком и по всем классам**, включая справочные (`gap_days` получает нефильтрованную выборку; при передаче только `problem` проверка стала бы мягче написанного — найдено `logic-auditor`, на текущих данных итог тот же): ноль по одной теме это затишье, ноль по всем сразу — отсутствие наблюдения, а не наблюдение нуля. Если окно медианы `[t−28, t−1]` хотя бы одним днём попадает в пропуск, в точке `t` всплеск не отмечается. Правило то же, что для первого месяца ряда: нет окна — нет детекции.

Отсечено **9 событий, все в Туркестане** (66 → 57): возобновление выгрузки 2025-06-30 давало ×75 по электроснабжению, ×55 по мусору, ×51 по воде при медиане окна 0.0 и длительности до 15 дней.

Два правила не пересекаются: без обоих 1 271 событие, только пропуски — 1 262, только первый месяц — 1 232, с обоими — **1 223**.

**Честная цена правила — одно вероятно настоящее событие.** Из девяти отсечённых восемь имеют медиану окна 0.0–2.0, то есть чистые артефакты. Девятое — Туркестан, водоснабжение, 2025-07-24: 90 обращений при медиане 38.5, кратность ×2.34. Его окно задето пропуском всего на 4 дня из 28, и без них медиана была бы 39.5 вместо 38.5 — то есть пропуск на оценку почти не влиял. Правило «любое пересечение с пропуском» намеренно консервативно; смягчение (порог по доле задетых дней) не вносилось — решение за основной сессией.

Итого **1 223 всплеска**. Максимум в год — Караганда 128, Павлодар 124; порог 200 не превышен. Кратность: медиана ×4.0, 90-й процентиль ×13.0, 99-й ×75.6. Прирост: медиана +26, 90-й +148, 99-й +512. Число всплесков менялось вместе с маппингом тем 2026-09-11: 1 231 → 1 234 после переноса `опор`/`утечк` (изменились ряды «безопасности» и «электроснабжения»), затем 1 234 → 1 233 после сужения `провод` (9 строк Караганды ушли из электроснабжения в ЖКХ), затем 1 233 → 1 232 после отсева сдвига полей Алматы (у Алматы 56 → 55); отсев сдвига у Караганды, ВКО и остатка Алматы итог не изменил, но у Караганды отсечка первого месяца 13 → 12 и `anomaly` 48 → 46.

### `spike_type` — правило V2

`seasonal` — в **большинстве** наблюдаемых прошлых лет в те же даты ±10 дней по этому же срезу был всплеск. `anomaly` — прошлые годы наблюдались, но всплеск был в меньшинстве из них. Пусто — сравнивать не с чем. Считается для Павлодара, Караганды и ВКО.

| Регион | seasonal | anomaly | без типа | Прошлых лет за меткой |
|---|---|---|---|---|
| Павлодарская | 346 | 289 | 125 | от 1 до 6 |
| Карагандинская | 65 | 46 | 115 | **ровно 1** |
| Восточно-Казахстанская | 31 | 19 | 27 | 1 или 2 |

**Пример неустойчивости метки внутри одного эпизода (найдено 2026-09-13 при сборке демо-сценария).** Павлодар, теплоснабжение, ноябрь 2022. Детектор видит здесь **три отдельных события**, а не одно: 17.11 и 19–21.11 ниже порога, поэтому череда подряд идущих дней разрывается. Каждое событие классифицируется независимо, и метки расходятся:

| Событие | Год −1 (2021), окно ±10 дней | Год −2 (2020) | Итог |
|---|---|---|---|
| 16.11 | 06.11–26.11 — **есть** 10.11 | есть, 4 дня | 2 из 2 → `seasonal` |
| 18.11 | 08.11–28.11 — **есть** 10.11 | есть, 6 дней | 2 из 2 → `seasonal` |
| 22.11 | 12.11–02.12 — **нет** | есть, 9 дней | 1 из 2 → `anomaly` |

**Вердикт решает один день.** В 2021 году в середине ноября был ровно один всплеск — 10.11.2021. Окно события 16.11 дотягивается до 06.11 и его ловит, окно события 22.11 начинается с 12.11 и промахивается на два дня. Прошлых лет всего два, а условие `попаданий × 2 > лет` при двух годах требует попадания в **оба**, — потеря одного года сразу переворачивает вердикт.

Следствие: **при двух годах истории метка неустойчива не только между регионами, но и внутри одного эпизода.** В демо-сценарии (`src/demo.py`) колонка типа скрыта — на показе объяснять это негде; в витрине она остаётся, там под неё есть блок «Как это считается».

**Метки регионов несопоставимы по силе.** За каждой меткой стоит разное число прошлых лет, в которых проверялось совпадение. У Караганды все 111 размеченных событий опираются ровно на один прошлый год, поэтому V2 («большинство лет») для неё **вырождается в V0** («хотя бы в одном году») — то самое правило, которое нулевой тест признал слабым. У ВКО один или два года; при двух годах ничья «1 из 2» по условию `hits·2 > obs` даёт `anomaly`. У Павлодара распределение по числу лет: 1 — 119 событий, 2 — 111, 3 — 122, 4 — 114, 5 — 121, 6 — 48. Сравнивать доли `seasonal` между регионами напрямую нельзя.

Всего `anomaly` — 354.

**Почему V2, а не «хотя бы в одном прошлом году» (V0).** Нулевой тест: даты всех событий сдвинуты на полгода, в противоположный сезон, и размечены заново. Для V0 Павлодар дал 77.8% `seasonal` по факту против 74.2% на сдвинутых датах — разрыв 3.6 п.п., правило почти не отличало сезонность от случайности. При шести годах истории и частых всплесках совпадение в окне ±10 дней почти гарантировано: 693 обращения 06.02.2023 становились «сезонными» из-за всплеска в 24 обращения в 2021 году.

| Правило | Павлодар факт | Сдвиг | Разрыв | Ключевые события верно |
|---|---|---|---|---|
| V0 любой прошлый год | 77.8% | 74.2% | +3.6 | 1 из 5 |
| V1 любой год, пик прошлого ≥ 50% | 67.4% | 60.7% | +6.7 | 3 из 5 |
| **V2 большинство прошлых лет — принято** | **55.0%** | **43.6%** | **+11.4** | **5 из 5** |
| V3 большинство лет и пик ≥ 50% | 36.9% | 27.8% | +9.0 | 4 из 5 |

Ключевые события: открытие сезона 2021 и 2023 — seasonal; ноябрь 2022, февраль 2023, вода июнь 2024 — anomaly. Замер разрыва выполнен до исправления маппинга тем; качественно на выбор правила это не влияет.

### Известные ограничения детектора

1. **Окно 28 суток не видит годовую сезонность.** Начало отопительного сезона каждый сентябрь выглядит как инцидент. В топ-10 по кратности среди всех типов такие события занимают 5 мест из 10. Разметка `spike_type` по правилу V2 частично это компенсирует, но только для регионов с историей больше года.

2. **Высокий зимний фон занижает кратность реальных аварий.** Павлодар, теплоснабжение, 22.11–03.12.2022: событие начинается 22.11 при медиане окна **7.0**, пик приходится на 30.11 — **480** обращений, и медиана окна **на дату пика уже 11.5**. Кратность ×68.6 считается как пик к медиане **на старте события**, то есть 480 / 7.0: это две разные даты, и подавать их как «480 при фоне 7» нельзя. В топ-10 по кратности среди всех типов не попадает. Шкала прироста и фильтр `anomaly` выводят его на 4-е место.

3. **Вырожденные случаи `MAD = 0`** — 26 из 1 223 (2.1%). Порог схлопывается до медианы, всплеском становится любой день с 10+ обращениями.

4. **Первый год ряда не классифицируется.** Нет прошлогоднего окна — нет типа. Поэтому без `spike_type` остаются оба сильнейших по кратности события: Павлодар, безопасность, апрель 2020, и Караганда, дороги, 31.12.2022. В топ `anomaly` они не попадают ни при каком правиле.

5. **Сдвинутое окно поглощает длительное событие.** По мере того как дни события входят в окно, медиана растёт — у экибастузского эпизода с 7 до 50.5 за три недели — и детектор перестаёт отмечать хвост, хотя счётчики остаются в 2.9–12.3 раза выше исходного фона (20–86 обращений в день при фоне 7). Отмечено 12 дней, повышенный фон держится около трёх недель. Не исправляется по решению основной сессии.

6. **ИСПРАВЛЕНО 2026-09-13: ложные всплески на возобновлении выгрузки.** В Туркестане нет обращений с 2025-01-01 по 2025-06-29 (180 дней), и на рестарте детектор отмечал события с медианой окна 0.0. Закрыто правилом «окно в пропуске — детекции нет», см. выше: снято 9 событий, итог 1 232 → 1 223, `MAD = 0` 33 → 26. Остаточный риск — пропуски короче 7 дней: они фон занижают, но правилом не ловятся.

7. **Кратность чувствительна к составу темы.** После исправления маппинга 2026-09-11 в «безопасность» вошли 2 042 строки «Правопорядок». Медиана окна перед апрелем 2020 выросла с 1.5 до 2.5, и кратность главного события упала с ×757 до ×454 при неизменных 1 136 обращениях. Любая правка маппинга тем меняет кратности — числа из детектора после такой правки перепроверять.

### Детектор — указание, куда смотреть, а не предупреждение о событии

Проверено отдельным прогоном 2026-09-18. Формулировка «детектор предупредил за N дней» не подтверждается, и на защите её использовать нельзя. Три числа:

1. **Подъём над базой падает вдвое, если база сопоставима.** Если сравнивать сигнальные дни со всеми наблюдаемыми днями подряд, доля «после сигнала в окне есть пик» выглядит на **33.2 п.п.** выше базы. Но начало серии сигналов — заведомо день высокой активности, а пики кучкуются в активные периоды. При базе из дней того же уровня активности подъём — **18.0 п.п.**
2. **Сила сигнала не упорядочивает результат.** Монотонный рост доли «пик после серии» с ростом силы первого сигнала держится только в **2 комбинациях из 12** (варианты определения пика × шкалы силы). Называть детектор «ранжированием по силе» данные не позволяют.
3. **Сигнал не единичен.** В ряду «Павлодар × теплоснабжение» до серии, начавшейся 22.11.2022, было **92 сигнальных дня**. Фраза «сигнал за 8 дней до пика» верна арифметически для этой серии, но пик 30.11 при окне сопоставления 14 дней попадает **внутрь той же серии** — сигнал описывает текущий подъём, а не предупреждает о другом событии.

Корректная формулировка: детектор показывает, **куда смотреть в первую очередь**; предсказания конкретной аварии он не даёт.

### Случай для защиты

**Павлодарская область, тема «безопасность», 18 апреля 2020.** Пик 27 апреля — 1 136 обращений при медиане 2.5, кратность **×454**, прирост +1 133.5, 13 дней подряд. В исходных данных 7 539 из 7 546 обращений периода — категория «Чрезвычайные случаи» (остальные: «Правопорядок» 4, «Пожар» 2, «Видеонаблюдение» 1; 4 строки «Правопорядок» вошли в тему после исправления маппинга, до него было 7 539 из 7 542). Совпадает по времени с режимом ЧП весны 2020; связь по данным не доказывается. `spike_type` отсутствует — первый год ряда. **Ранее здесь стояло ×757** — это значение до исправления маппинга тем, см. ограничение 6.

### Павлодар, теплоснабжение, 15.11–15.12.2022 — проверка детектора на известном событии

**Это единственный случай в выгрузке, где сработку детектора можно сопоставить с публично задокументированным происшествием.** Поэтому эпизод остаётся здесь как проверка метода, даже после того как сквозной сценарий для показа перенесён на Костанай (раздел 5j): демонстрационная ценность и проверочная — разные вещи, и вторая от переноса не исчезла. `src/demo.py` ссылается на этот разбор строкой на экране.

Фон 3–14 обращений в день до 21.11, не считая отдельных всплесков 16.11 (30) и 18.11 (32). Рост с 22.11 (36), ускорение 26–29.11 (80, 97, 60, 122), **пик 30.11 — 480** (медиана окна на эту дату 11.5, а не 7.0 — 7.0 относится к 22.11), затем 01.12 — 394, 02.12 — 237, 03.12 — 125. Детектор отмечает 22.11–03.12 и отдельно 16.11 и 18.11. После 03.12 фон 20–86 обращений в день — от ×2.9 до ×12.3 к исходным 7 — держится до ~12.12. Всего за 31 день — 2 444 обращения. По правилу V2 событие 22.11.2022 — `anomaly`. Совпадение с аварией на ТЭЦ Экибастуза — гипотеза, проверяется у заказчика.

## 5g. Прогноз нагрузки (2026-09-12)

`src/forecast.py`. Запуск: `.venv/bin/python -m src.forecast [--horizon 13] [--folds 3] [--keep-first-month]`. Выход — `reports/forecast.md`. Прогон воспроизводим: повторный запуск даёт байт-в-байт тот же отчёт.

Ряды: обращения класса `problem` по неделям (неделя помечена датой понедельника, которым заканчивается), разрез регион и регион × тема для пяти крупнейших тем. Неполные крайние недели и первый календарный месяц ряда отброшены — как в детекторе всплесков.

### ДЛЯ ПОКАЗА ЗАКАЗЧИКУ — одна строка

**На горизонте квартала уровень обращений в основном держится на уровне последних недель, и прогнозная модель этого не улучшает. Модель нужна на переходах между сезонами, где плоский прогноз ошибается в разы.** Пример — теплоснабжение Павлодара: 3 обращения в неделю в июле против 352 в октябре; плоский прогноз даёт на квартал десятки обращений при фактических 423–3 618 в прошлые годы.

### Где считается

| Регион | Недель | Прогноз |
|---|---|---|
| Павлодарская | 333 | строится |
| Восточно-Казахстанская | 142 | строится |
| Карагандинская | 99 | строится, **ряд на грани**: на скользящую проверку остаётся 2 отсечки, не 3 |
| Туркестанская | 88 | **не строится: пропуск в выгрузке**, см. находку ниже |
| Алматинская / Костанайская / Акмолинская | 40 / 39 / 13 | не строится: нужно минимум 78 недель (52 лаг + 13 горизонт + 13 на поправку уровня) |

Итого 14 срезов: Павлодар 6, Караганда 6, ВКО 2.

### НАХОДКА: у Туркестана в выгрузке полгода без единого обращения

**2025-01-01 → 2025-06-29, 180 дней подряд, 27.4% окна региона.** Остальные шесть регионов чисты: подряд идущих пропусков в 7+ дней нет нигде.

Ряд разорван пополам, прогноз по нему строить нельзя: обучающее окно попадает в пропуск, плоская и сезонная модели начинают предсказывать нули (в первом прогоне обе давали ровно 0 и MAE 894 против 152 у наивного). Регион исключён автоматически — правило `longest_gap` > 4 недель, а не вручную.

**Тот же пропуск портит детектор всплесков.** На возобновлении выгрузки 2025-06-30 детектор отмечает 7 ложных всплесков с медианой окна 0.0 и «кратностью» ×75, ×55, ×51, ×24 длительностью до 15 дней. Они входят в текущие 1 232 всплеска. Не исправлено — решение основной сессии не принято.

### НАХОДКА: у ВКО состав потока меняется в течение 2023 года

**Доля темы «ЖКХ» внутри класса `problem`: 27% в 2023 году → 99% в 2025.** Число различных значений `category` в квартале упало с 18 (2023Q1) до 4 (2025Q4). «Связь и информация» обрывается после 2023Q3 (1 642 строки в квартале → 15 → 0), «Дороги» 2 108 → 57, «Экология» 339 → 33 → 0; «Справка» растёт с 1 814 до 10 893 в квартале.

Это смена справочника или практики регистрации в системе-источнике, а не изменение того, на что жалуются люди.

**Единой границы 2023Q4 нет — исправлено 2026-09-18 по итогам пересчёта.** Каждая тема меняется в свой квартал: «Дороги» между 2023Q1 и Q2, «Экология» в 2023Q3, «Связь» в 2023Q4, «ЖКХ» не падает, а растёт. Число значений `category` в квартале снижается неравномерно и в 2024Q2 составляет 19 — больше, чем в начале периода. Разбор по темам с числами — раздел 10, пункт 8.

Следствия: разрез по темам ВКО через 2023 год требует проверки по каждой теме отдельно, общего «до и после» у региона нет; срез «ВКО × ЖКХ» почти повторяет регион целиком (прогноз 1 424 против 1 436). Прогноз по региону в целом это не ломает. Проверка встроена в скрипт: сдвиг доли главной темы больше 30 п.п. помечается автоматически — он отмечает факт сдвига, но не датирует его одним кварталом.

Отдельно: четыре темы из топ-5 ВКО (связь 5 122 обращения, дороги 1 984, экология 1 977, безопасность 276) в типичную неделю дают меньше 10 обращений — приходят пачками, а не потоком. По ним прогноз не строится: MAE исчисляется единицами обращений, и «лучшая модель» выбиралась бы шумом. В отчёте они перечислены отдельной таблицей.

### Три модели, намеренно простые

| Модель | Формула | Смысл |
|---|---|---|
| наивный | ŷ(t) = y(t−52) | «столько же, сколько в этот период год назад» — базовая линия из постановки |
| сезонный | ŷ(t) = y(t−52)·k, k = медиана(13 нед.) / медиана(тех же 13 год назад) | то же с поправкой на текущий уровень |
| плоский | ŷ(t) = медиана последних 8 недель | контроль: нужна ли годовая сезонность вообще |

### Главный результат: сезонность не окупается

По средней MAE на скользящей проверке **плоский прогноз лучший на 13 срезах из 14**, сезонный на 1, наивный на 0.

**Пересчитано 2026-09-13 после правок аудита — вывод устоял.** Сравнение прогнали на обеих версиях кода подряд, на одних и тех же рядах:

| | наивный | сезонный | плоский | наивный не хуже сезонного |
|---|---|---|---|---|
| до правок | 0 | 1 | 13 | 8 из 14 |
| **после правок** | **0** | **1** | **13** | **8 из 14** |

Лучшая модель не сменилась ни на одном срезе. Изменилось одно число из 42: MAE сезонного на теплоснабжении Павлодара, 132 → 46 — там защита уровня теперь работает и в проверке тоже. Победителя это не тронуло: плоский там 25 в обеих версиях.

Две остальные правки эту таблицу задеть и не могли: `evaluate_at` вызывает только `forecast` и `metrics`, а `crosses_transition` и `monthly_profile` живут в таблице переходов и в выборе модели для прогноза вперёд. Проверено по графу вызовов, а не на слово.

**Наивный прогноз не проигрывает сезонному:** лучше или равен на 8 срезах из 14. Поправка на уровень себя не окупает. Так и докладывать — это прямой ответ на вопрос из постановки.

Качество на последней отсечке (13 недель, лучшая модель среза): MAPE от 13.8% (Караганда · связь) до 62.2% (Павлодар · теплоснабжение). По регионам целиком: Павлодар 19.2%, Караганда 17.2%, ВКО 38.7% — все три на плоском.

### Где плоский прогноз ломается — и как это поймано

Вывод «плоский лучше» получен в среднем, а среднее берётся по отсечкам, которые почти не пересекают смену сезона. У Павлодара теплоснабжение идёт 3 обращения в неделю в июле против 352 в октябре, и окно прогноза вперёд (2026-07-20 + 13 недель) попадает ровно на этот переход.

**Правило выбора модели для прогноза вперёд:** если типичный уровень месяца на конце окна отличается от уровня месяца на старте в 3 и более раз — модель выбирается по отсечкам **того же календарного перехода** в прошлые годы (у теплоснабжения таких 21 за 5 лет), а не по среднему результату скользящей проверки. Усреднять все переходы подряд нельзя: вход в сезон и выход из него — разные задачи, ошибки гасят друг друга.

**Защита поправки на уровень.** Если k считается по межсезонью с единицами обращений в неделю — она отключается, модель вырождается в наивную. У теплоснабжения k = 2.50 получалось из медиан **5 и 2 обращения в неделю** и множилось на пиковую базу, включающую неделю в 813 обращений: прогноз выходил 3 628 за квартал при историческом разбросе 423–3 618. Порог `MIN_LEVEL` = 10 обращений в неделю — тот же, что `--min-count` у детектора всплесков, а не новая подобранная константа.

### Сверка прогноза с фактом того же окна в прошлые годы

Отдельная таблица: прогноз против фактических сумм за то же календарное окно в прошлые годы, плюс факт последних 13 недель и факт того же окна год назад. **Выход выше диапазона прошлых лет — не дефект:** у растущего ряда это закономерно (Павлодар: последние 13 недель 27 658 против максимума прошлых лет 24 303). Разбирается обратный случай.

Два среза дали прогноз ниже всех прошлых лет, и причины у них **разные**:
- **Караганда · дороги** — уровень окна декабрь→март растёт ×2.2, порог ×3 не пройден, плоский прогноз в сезон не входит. Это промах правила у границы порога.
- **Караганда · связь** — перепада уровня нет (×1.0), ряд просто идёт ниже прошлых лет: 943 за последние 13 недель против минимума 1 193. Прогноз следует за фактом.

### Исправлено по итогам аудита 2026-09-13

Три находки `logic-auditor`, все подтверждены независимым пересчётом:

1. **Заглядывание в будущее в `transition_folds`.** Решение «эта прошлая отсечка пересекает смену сезона» принималось по профилю месяцев ВСЕГО ряда, включая данные после отсечки. На теплоснабжении Павлодара решение менялось у 6 отсечек из 128. Теперь профиль считается по ряду до отсечки.
2. **Защита уровня действовала только в прогнозе вперёд, но не в бэктесте.** Модели сравнивались в одних условиях, а применялись в других: на теплоснабжении уровень ниже `MIN_LEVEL` держится на 102 отсечках из 256. Защита перенесена внутрь модели (`level_guarded`), теперь одинакова везде. MAE сезонного на теплоснабжении по скользящей проверке упал со 132 до 46 — прежнее число мерило не ту модель, которая пошла бы в работу.
3. **Профиль месяца мерил тренд, а не сезон.** На абсолютных медианах растущий ряд даёт «смену сезона» между любыми далёкими месяцами: у социальных вопросов Павлодара при сезонности ×1.15 набиралось 22 «переходных» отсечки — июнь 47 против сентября 15.5 на train в 67 недель, то есть рост 2021 года. Профиль переведён на отношение к скользящему годовому уровню, плюс требование минимум 2 разных лет наблюдений на каждый сравниваемый месяц. Переходных отсечек у социальных вопросов осталось 5, у теплоснабжения 74.

**Правка 2 сломала функцию и была поймана чтением, а не прогоном:** при вставке `level_guarded` строка `raise ValueError(model)` уехала внутрь новой функции мёртвым кодом, а `forecast()` потерял проверку неизвестной модели. Синтаксис при этом валиден, и `ast.parse` прошёл.

### Исправления, сделанные по ходу

- **Профиль месяца считается по медиане, а не по среднему.** На среднем критерий смены сезона срабатывал от одного выброса: у Караганды март 2022 содержит неделю в 1 460 обращений по дорогам, среднее марта 375 против медианы 170 при медиане ряда 78, и переход декабрь→март ложно проходил порог (×3.89 против ×2.18 по медиане). Медиана согласована с остальным кодом — плоская модель, поправка k и детектор всплесков тоже медианные.
- **Плоская модель исключается, когда окно пересекает смену сезона, а отсечек того же перехода в ряду нет.** Плоский прогноз — константа, перепад уровня в разы он не отследит независимо от того, что показала скользящая проверка. На текущих данных эта ветка не срабатывает, но дыра в логике была реальной.

### Известные ограничения

1. **У Караганды прогноз вперёд — проверка метода, а не рабочий прогноз:** данные заканчиваются 2023-12-25, окно уходит в начало 2024 года, которого в выгрузке нет.
2. **База наивного и сезонного прогнозов копирует разовые выбросы.** Недели выше 5 медиан ряда в базе: Павлодар · вода 1 292 (×5.0), Павлодар · теплоснабжение 813 (×30.1), Караганда · дороги 1 913 (×24.5). Лечится винзоризацией или медианой нескольких прошлых лет — не делалось: сезонность и так не окупается.
3. **Порог ×3 — граница, и у неё всегда есть срезы чуть ниже** (Караганда · дороги, ×2.2). Ловится только сверкой с фактом того же окна.
4. **Скользящая проверка Караганды опирается на 2 отсечки** — при 99 неделях и горизонте 13 больше не помещается. Вывод «плоский лучший» по Караганде слабее, чем по Павлодару и ВКО.
5. **Сравнение объёмов между регионами по-прежнему некорректно** — см. раздел 5d; прогнозы разных регионов не складывать и не ранжировать.

### Оговорки считаются из данных, а не пишутся под вопрос

Каждый ответ сопровождается предупреждениями, которые вычисляются на лету:
- заполненность каждого использованного поля, если она ниже 95% (`district` 22.2%, `executor` 29.7%, `sla_breach` 7.3%, `status` 85.5%);
- сколько регионов из семи покрывает запрошенный период — вопрос «за прошлый месяц» на опорной дате 2026-07-26 попадает в окно, где есть данные **одного региона из семи**;
- пропуски в выгрузке, пересекающиеся с периодом (Туркестан, 180 дней — см. 5g);
- несопоставимость объёмов регионов (раздел 5d) для любого разреза по регионам.

### Разрез по темам считается по классу problem

Без этого фильтра на вопрос «доля трёх крупнейших тем» первой выходит «прочее» с 34.3% — это справочный трафик и служебные артефакты, у которых темы нет. С фильтром ответ 54.6% на три темы (электроснабжение, вода, мусор), что сходится с распределением раздела 5e: 21.91 + 20.88 + 11.81 = 54.60%. Фильтр подставляется автоматически и **виден в показанном запросе**, а не спрятан.

### Исправлено по итогам аудита 2026-09-13

- **Доля названной темы возвращала долю крупнейшей.** На вопрос «какая доля обращений про воду» headline-числом было 21.9% — доля электроснабжения, потому что фильтр по теме снимался как совпадающий с полем группировки, а `number` брался как первая строка разбивки. Добавлено поле `focus`: теперь 20.9% и названа именно вода.
- **«Перестали приходить» на периоде короче года давало «таких тем нет» при любых данных.** Окно сравнения жёстко 6 месяцев, а вычиталось от конца периода: на квартальном периоде половина «до» оказывалась пустой всегда. Теперь при периоде короче двух окон — отказ с объяснением, а не правдоподобный отрицательный ответ.
- **Оговорка по `sla_breach` не говорила главного.** Сводные 15.2% просрочки считаются по двум регионам, у которых доли расходятся в 4,677 раза без объяснения (раздел 3). Оговорка теперь вычисляется: называет регионы, их доли и величину расхождения, и прямо говорит, что приводить сводное число как общий уровень просрочки нельзя.

### Найденные и исправленные ошибки самого модуля

- «Какие пять тем дают больше всего обращений» разбиралось как «пиковый день»: шаблон `больше всего обращений за` стоял раньше разреза по темам. Теперь пиковый день требует слова о времени («когда», «день», «дата», «пик»).
- Вопрос про долю трёх крупнейших тем выдавал все 15 тем вместо суммы трёх — не было разбора числительных.
- Разрез «в разрезе регионов» выдавал только лидера; теперь перечисляются все строки ответа.
- `.replace(",", " ")` применялся ко всей строке ответа и съедал запятые перечислений. Вынесено в отдельный форматтер `num()`.
- «Прочее» выходило первым в рейтинге роста тем (+146.7%). Это не тема, а остаток маппинга: из рейтингов исключено, но его величина уходит в оговорку — рост «прочего» показывает качество разметки и смотрится отдельно. При этом знаменатель доли берётся ДО исключения: вопрос «доля всех обращений» спрашивает про всё, и уменьшать целое под красивую долю нельзя (54.6% от 658 103, а не 55.5% от 647 128).
- Среднее в день по годам сравнивало годы с разным числом регионов в выгрузке (2020: 1, 2025: 6). Добавлена автоматическая оговорка — иначе рост среднего читается как рост нагрузки.

| **Всплесков требуют внимания** | длина секции «Требует внимания» при текущих фильтрах ленты; подпись — за сколько дней, по регионам и почему даты у регионов разные | **9** (за 7 дней: Павлодар 4, Караганда 3, Алматы 2); при 30 днях — 38 |

Шапка стоит на странице первой, но заполняется после ленты и блока риска: `st.container()` создаётся в начале, карточки рисуются в него, когда секция «Требует внимания» и рабочая точка уже посчитаны. Так число в карточке не может разойтись с блоком — проверено на пяти состояниях фильтров ленты (по умолчанию, сортировка по кратности, без Павлодара, Павлодар за 1 день, без регионов): **5 из 5 совпали**. Карточка риска и строка под таблицей блока риска совпадают: 4 048 и 76%.

**Решения, принятые при сборке шапки:**
- **«Самый сильный» — только из региона с самыми свежими данными (правка 2026-09-25).** Первая версия брала первое событие всей секции «Требует внимания» и показывала декабрь 2023 у Караганды: «последние дни» у неё — это конец её выгрузки, а не сегодняшний день. Теперь регион — с самой поздней датой данных среди выбранных в ленте (по умолчанию Павлодар, по 26.07.2026; без Павлодара — Алматы, по 11.11.2025). Если у него за окно всплесков нет, карточка говорит «свежих всплесков нет» словами и называет регион и дату.
- **Внутри региона «самый сильный» — первый в текущем порядке ленты.** По умолчанию лента сортируется по числу жалоб сверх обычного — шкала для показа из 5f. У Павлодара за 7 дней шкалы расходятся: по приросту первое — благоустройство (+45, в 2.9 раза), по кратности — жилищный фонд (+38, в 10.5 раза). Переключатель порядка в ленте меняет и карточку.
- **Третья карточка — очередь на проверку, а не прогноз по всей базе (правка 2026-09-25).** Первая версия показывала всё, что модель отмечает на своём пороге, — 10 777 из 20 238, больше половины потока. Теперь — рабочая точка 20% из раздела 6b: 4 048 обращений. 10 777 и порог 0.48 остались в блоке риска: число — простой строкой, порог и TP/FP — в «Как это считается». Это не текущая очередь: период проверки модели — обращения Караганды с 01.07.2023, новее данных нет, подпись говорит об этом прямо.
- **«Кликом — переход к ленте»** сделан ссылками на якоря заголовков (`#vspleski`, `#risk`): карточка streamlit сама не кликается.
- Под карточками — одна строка: что это за система, по каким областям данные и общий период.

**Найдено при перестановке и исправлено — дефект старого кода:** пока в календаре «Период» выбрана только начальная дата, `date_input` отдаёт одну дату, переменные границ периода не определялись, и витрина падала с `UnboundLocalError` на выгрузке — всё ниже неё исчезало. Заодно убран `st.stop()` при пустой выборке фильтров: при новом порядке он скрыл бы «Общие цифры», которые от фильтров не зависят; вместо него пустые графики и выгрузка показывают сообщение.

### Лента событий и «требует внимания»

Колонки ленты: начало, день пика, регион, тема, жалоб в день пика, обычно в день до начала (медиана окна на старте), во сколько раз больше обычного (кратность), жалоб сверх обычного (прирост), длилось дней, характер (тип). Сортировка по умолчанию — по абсолютному приросту («по числу жалоб сверх обычного»), переключатель на кратность. Фильтры: регион, тема, период, характер, минимальная кратность («жалоб больше обычного хотя бы во столько раз»).

**Уведомление — это состояние в интерфейсе, не рассылка.** События последних N дней (по умолчанию 7, задаётся в интерфейсе) помечаются новыми и выносятся наверх отдельной секцией. Отправка наружу не делается: адресатов нет, и права рассылать эти данные у нас нет.

**Отсчёт «новизны» идёт от последнего дня данных КАЖДОГО региона, а не от сегодняшней даты.** Выгрузка историческая и заканчивается в разное время: Караганда 2023-12-31, Туркестан 2025-10-19, ВКО 2025-10-31, Акмола и Костанай 2025-11-05, Алматы 2025-11-11, Павлодар 2026-07-26. От общей последней даты секция показывала бы только Павлодар. Даты выведены подписью под секцией, чтобы это не пришлось угадывать. При N = 7 новых событий 9, при N = 30 — 38.

По клику на строку раскрывается ряд за две недели до и две после: столбцы по дням, дни всплеска красным, линии медианы окна и порога. Тот же вид, что в разборе экибастузского эпизода — на нём и проверено: в окне ±14 дней вокруг 22.11.2022 детектор отмечает 14 дней (12 подряд плюс 16.11 и 18.11).

Блок «Как это считается» в интерфейсе раскрывает правила детектора: сдвинутое окно, отключение детекции в первый месяц ряда и на пропусках выгрузки, смысл типов и оговорку о несопоставимости меток между регионами.

**Три отступления от исходной постановки блока, все — из-за того, что лежит в готовых файлах:**

3. **Precision в топ-10% берётся из `predictions.csv`, а не из `metrics.json`** — в `metrics.json` её нет. Считается той же функцией, что строка под таблицей.

## 5j. Сквозной сценарий для защиты (2026-09-13, перенесён на Костанай 2026-09-20)

`src/demo.py`. Запуск одной командой: `.venv/bin/python -m src.demo` — **141 секунда**, лимит показа три минуты. Паузы не заданы числом, а выводятся из бюджета: модули 1–2 укладываются в `ROUTE_BUDGET` = 35 с, модуль 3 — в `STREAM_BUDGET` = 80 с, пауза = бюджет / число дней, но не больше 1.6 с. При 58 днях показа это 0.6 с в модулях 1–2 и 1.4 с в модуле 3. Так лимит держится и если окно показа поменяют. Флаги: `--pause 0` для проверки, `--no-export` без сборки файлов.

**Сценарий проходит все три модуля ТЗ подряд, на одном эпизоде и одном потоке обращений**: модуль 1 — приём и маршрутизация, модуль 2 — ассистент оператора, модуль 3 — детектор, витрина и выгрузка. Первые два работают **на метаданных, а не на дообученных моделях**, и прогон говорит об этом вслух: текста обращений в выгрузке нет (55 строк на 1 063 216, раздел 5b), поэтому ни классификатор по тексту, ни эмбеддинги для похожести обучать не на чем.

**Эпизод: Костанайская область, благоустройство и озеленение, 29.09.2025** — 180 обращений за день при фоне 4.0, кратность **×45.0**, прирост +176, длительность 5 дней. Окно показа **11.08–07.10.2025**, 58 дней.

### Почему Костанай, а не Павлодар (перенос 2026-09-20)

Первая версия сценария шла по Павлодару (теплоснабжение, ноябрь 2022 — эпизод, совпавший по времени с аварией на ТЭЦ Экибастуза). Эпизод был эффектный, но у Павлодарской области **пустые поля**: `executor` заполнен в 0,00% строк, разметки просрочки нет вовсе. Из-за этого модуль 1 показывал «поля нет» вместо ответственной службы, а приоритет считался переносом разметки Костаная и Туркестана — с обязательной оговоркой про расхождение в 4,677 раза.

У Костаная `executor`, `district`, `status` и `sla_breach` заполнены на **100%**. Три следствия, каждое видно в прогоне:

| | Павлодар (было) | Костанай (стало) |
|---|---|---|
| Ответственная служба | «поля нет», `executor` 0,00% | настоящее название, `executor` 100,00%, 117 исполнителей |
| Приоритет темы | перенос чужой разметки, оговорка про 4,677 раза | собственная разметка региона, `sla_breach` 100,00% |
| Тип события в ленте | скрыт: метки при двух годах истории неустойчивы | скрыт: у региона меньше года, тип не определён ни у одного события |

**Почему не Караганда — разбор зафиксирован, чтобы не пересматривать заново.** Кандидатов с заполненным `executor` выше 80% было четыре: Костанай и Туркестан (100%), Караганда (99,57%), ВКО (93,39%). Караганда выглядела сильнее всех по эффектности — 27 событий с кратностью от 10 против 7 у Костаная, сильнейшее ×286,8, и это единственный регион, где обучена модель риска просрочки. Отвергнута по двум причинам: у неё **нет разметки просрочки** (`sla_breach` пуст, приоритет снова пришлось бы переносить), а сильнейшее событие приходится на **31.12.2022 — последний день ряда**, что на показе неотличимо от новогоднего артефакта и требует объяснений вместо демонстрации. Туркестан отпал из-за медианы окна 0.0 в сильнейшем событии (вырожденный случай `MAD = 0`) и полугодового провала выгрузки. ВКО — из-за смены состава потока в 2023 году (раздел 5g). Осталось три требования, и Костанай — единственный, кто выполняет все: **собственная разметка просрочки, `executor` 100%, дата события без календарных артефактов.**

**Эпизод Экибастуза из сценария убран, но не потерян:** он остаётся в разделе 5f как проверка детектора на событии с известной внешней хроникой — это единственный случай в выгрузке, где сработку детектора можно сопоставить с публично задокументированным происшествием. Прогон ссылается на него строкой на экране.

### Модуль 1 — приём и маршрутизация

Для первого обращения каждого из 58 дней печатается путь: время поступления и исходное значение `category` → тема и класс живым вызовом `map_topic()` / `classify_appeal()` → ответственная служба из `executor`.

Приоритет считается из данных, порог не подбирается: тема приоритетна, если её доля просрочки выше средней по региону **34,94%** (20 544 размеченных обращения) при базе **не меньше 100** размеченных обращений по теме. Приоритетных тем 5. Тема эпизода «благоустройство и озеленение» — **45,39%** на 2 866 обращениях, приоритетная; «экология» с 85,7% не засчитана, под ней 7 обращений.

**Разметка собственная, перенос не нужен.** `sla_breach` заполнен у Костаная на 100%, поэтому и база, и доли по темам считаются по нему самому. Расхождение 34,9% / 7,5% между Костанаем и Туркестаном (раздел 3) на этот расчёт не влияет — чужая разметка не используется. Прежняя оговорка про 4,677 раза из прогона убрана вместе с переносом.

### Модуль 2 — ассистент оператора

Для того же обращения ищутся похожие: тот же регион и тема, тот же район, окно 14 суток до обращения; выводится до пяти ближайших с датами и статусами. Развёрнутый список — на первом дне показа и на дне первого сигнала, дальше сводной строкой, иначе проход не укладывается в лимит.

**Район включён в поиск, но ничего не сужает.** У Костаная `district` заполнен на 100%, однако значение одно на весь регион — «КОСТАНАЙ». Разреза по районам внутри области эта выгрузка не даёт, и прогон говорит об этом прямо: иначе «ищем по региону, теме и району» звучало бы содержательнее, чем есть. Запрос к заказчику на фактическое значение района — раздел 10, пункт 10.

**Счётчик похожих следует за событием, а не опережает его.** В первый показанный день похожих 97, в последний — 389. Окно смотрит назад, поэтому счётчик показывает масштаб уже случившегося. Называть его ранним предупреждением нельзя — это та же ошибка, что «детектор предупредил за N дней» (раздел 5f).

**Заглушек нет ни на одном шаге.** Обращения читаются из `data/unified.parquet` вместе с настоящим временем и значением справочника; тема и класс присваиваются живым вызовом `src.topic_mapping`; всплески ищет живой `src.spikes`; отчёты собирает живой `src.export`; лента печатается через `feed_view` из `src.dashboard`.

### Почему показ начинается раньше эпизода

**Старт 11.08, за 49 суток до эпизода.** `DAY_FROM` задаёт только окно ПОКАЗА: детектор всё это время видит весь ряд среза с 01.02.2025, и окно `[t−28, t−1]` полное при любом старте после первого календарного месяца.

Дата выбрана из двух условий сразу: окно медианы полное уже в первый показанный день, и **предыдущий сигнал по этому же срезу — 15.08 — попадает внутрь показа**, а не остаётся за его границей.

Это правило пришло из павлодарской версии, где ошибка уже случалась: при старте 12.11 показ скрывал три более ранних сигнала по той же теме (10.10 ×6.9, 28.10 ×4.3, 06.11 ×3.7), и фраза «детектор поднял первый сигнал» была верна только для окна показа. Теперь прогон печатает это явно: **до окна показа детектор отметил 5 событий** (17.03 ×9.5, 01.04 ×4.8, 05.04 ×12.2, 14.04 ×4.0, 29.04 ×3.0), в самом окне — 3. Вопрос «а раньше сигналов не было?» получает ответ с экрана.

### Дубликаты по каноническим метаданным не выявляются

Проверка на повтор была реализована и **убрана из сценария 2026-09-20**: она ничего не различает. На Павлодаре из восьми канонических полей заполнены пять — `region`, `category`, `status`, `topic`, `appeal_class`, — и «вероятным дубликатом» оказывались **777 из 783** похожих, то есть 99%.

**Полнота полей эту проверку не спасает.** У Костаная заполнены **все восемь** канонических полей, и всё равно **33 из 54** похожих обращений накануне эпизода (61%) совпадают по всем ним; различает их только время поступления. Это и есть ответ на возражение «дело в пустых полях Павлодара» — дело не в них.

Чтобы выявлять повторные обращения, нужен **адрес или идентификатор заявителя**. И то и другое — персональные данные, в канон они не переносятся (раздел 1). Запрос к заказчику о приемлемой форме передачи — раздел 10, пункт 9.

### Колонка типа события в показе скрыта

В ленте демо-сценария колонки `тип` (в витрине с 2026-09-25 — «характер») нет. У Костаная выгрузка короче года, прошлых лет для сравнения нет вовсе, и тип не определён ни у одного события окна — колонка была бы столбцом «без типа». В павлодарской версии причина была другая и более тонкая: при двух прошлых годах метки расходятся внутри одного эпизода (пример в 5f). В витрине колонка остаётся в обоих случаях — там под неё есть раскрывающийся блок «Как это считается».

### Границы показа — проговорены в самом прогоне

1. **Сборка канона адаптером не проигрывается поштучно.** Адаптер разбирает файл региона целиком; это пакетный шаг. В сценарии обращения берутся уже из канона, а живьём показана классификация. Имитацию адаптера не ставили — вместо неё оговорка на экране.
2. **Витрину в терминале показать нельзя** — это веб-страница. Данные её ленты печатаются теми же функциями, что рисуют её на экране, и рядом выводится команда запуска.

Обе оговорки печатаются самим сценарием, а не только записаны здесь: на защите их видно на экране.

### ДЛЯ ЗАЩИТЫ: почему внешние корпуса — чужой предметной области

Пункты 1–2 проверены поиском 2026-09-20, пункт 3 — прямыми запросами к источникам 2026-09-25. Не предположения.

1. **Открытого корпуса обращений граждан со свободным текстом не существует ни на одном языке.** Ближайший класс систем — муниципальные службы 311 — публикует **ровно ту же структуру, что наша выгрузка, и по той же причине**. У NYC 311 поля `Problem`, `Problem Detail`, `Additional Details` — три уровня справочника, а единственное свободнотекстовое поле `Resolution Description` содержит ответ ведомства, не слова гражданина. У LA 311 (1,35 млн строк, GPL-3.0) — только `RequestType` из фиксированного списка. Текст заявителя вычищается перед публикацией, потому что содержит персональные данные. То есть отсутствие текста у нас — не дефект этой конкретной выгрузки, а общее свойство предметной области.
2. **Корпуса с казахским языком, метками и нужным объёмом нет.** В MASSIVE 51 язык, `kk-KZ` среди них отсутствует. 3. **В открытых источниках Казахстана текста обращений нет.** Проверено 2026-09-25 прямыми запросами, а не только поиском:

### Контракт входа — не меняется при переходе на реальные данные

Пайплайн не знает про корпуса. Принимает CSV и имена колонок флагами: `--text-col` и `--label-col` обязательны, `--id-col`, `--time-col`, `--split-col` опциональны.

- **Метка — строка, не int.** Кодирование в индексы внутри пайплайна, таблица соответствия — в артефакт. Готовые int приняли бы молчаливый переезд классов при смене корпуса.
- **`--time-col` заложен сейчас, хотя оба корпуса времени не имеют.** У обращений разбиение обязано быть временным, как в `train.py`. Режимы `--split-mode stratified|temporal` существуют с первого дня, иначе при подстановке реальных данных переписывать пришлось бы ровно то, от чего зависят выводы.
- **Дедупликация до разбиения**, число снятых строк печатается. В `unified.parquet` 3 726 строк входят в группы полных повторов (раздел 5c) — на реальных данных сработает сразу.
- **Редкие классы** — правило, а не решение по ходу: меньше `--min-class-count` (по умолчанию 10) → отброс или слияние в `__rare__` по флагу, с печатью списка.

### Метрики и доказательство работоспособности

Основная — **macro-F1** (при перекосе классов accuracy льстит, та же логика, что «прирост считать от PR-AUC» в 4b). Справочно accuracy и micro-F1, плюс таблица precision/recall/F1/support по каждому классу и топ пар ошибок.

Работоспособность доказана при пяти условиях: loss падает и val macro-F1 выходит на плато; обход «самого частого класса» с большим отрывом; не хуже TF-IDF + логрега; **перемешивание меток роняет macro-F1 к `1/классов`**; **прогоны совпадают в пределах измеренного шума, и величина шума указана** (замер ниже, «Шум по seed»). *Прежняя формулировка «два прогона с одним seed дают одинаковые метрики» снята 2026-09-22: на MPS повтор того же seed не воспроизводится бит в бит, а разброс между seed оказался одного порядка с проверяемым эффектом.* Четвёртое условие — главное: без него первые три одинаково хорошо выглядят и при работающем обучении, и при утечке.

### Артефакты

`models/finetune/<корпус>-<модель>-<дата>/`: веса и токенизатор, `label_map.json`, `run.json` (гиперпараметры, seed, версии, размеры выборок, снятые дубли), `metrics.json`, `report.md`, `predictions.csv`.

Применение — отдельная точка входа `predict` с теми же флагами колонок; метки берутся **из `label_map.json` артефакта**, никогда из новых данных.

**Правило коммитов действует с первого дня:** `metrics.json` и `report.md` — агрегаты, коммитить можно; `predictions.csv` — строка на пример, нельзя (раздел 1). Когда придёт настоящий текст, `predictions.csv` будет содержать ПДн, и менять правило будет поздно.

### Окружение

Зависимости вынесены в **`requirements-ml.txt`** отдельно от `requirements.txt` — витрине torch не нужен. Место на диске — раздел 0. Обучение идёт на Apple Silicon через MPS: **fp16 и bf16 не включаем**, считаем в fp32, поэтому маленькая модель не роскошь, а условие.

### Рабочие гиперпараметры и фактическое время (прогоны 2026-09-21)

**MASSIVE + `rubert-tiny2`: `--lr 2e-4 --epochs 15`, эпоха выбирается по валидации.** Дефолтные `lr 5e-5, 5 эпох` **не работают**: macro-F1 0.5319 против 0.7947 у TF-IDF, то есть хуже дешёвой базовой линии. Это недообучение, а не потолок модели — loss падал до последней эпохи, val macro-F1 рос до последней. У tiny2 29 млн параметров, большая часть в эмбеддингах, и ей нужен шаг на порядок крупнее.

**Фактическое время — 8 минут на 15 эпох (477 с обучения, 522 с прогон целиком), M5, MPS, fp32.** *Прежняя оценка «3–8 минут» была на 5 эпох, то есть на конфигурации, которая заведомо недообучается; сравнивать с ней нельзя.* Скорость 11,5–12,0 шаг/с, счётчик после 100 шагов предсказал 7,3 мин при фактических 8,0. Оценка ГРНТИ + tiny2 «20–40 минут» не подтвердилась: фактически 46,7 мин на 10 финальных эпох плюс 56 мин подбора lr (см. «(e) ГРНТИ» ниже).

Валидация выбирает **6-ю эпоху из 15**: дальше val macro-F1 колеблется в пределах 0.808–0.824, пока train loss падает до 0.003. Прогонять больше 8 эпох смысла нет.

### Выбор по валидации ухудшил оба числа — и это правильный результат

Первый прогон брал **последнюю** эпоху и **произвольное** `C=4` у базовой линии. После того как и то и другое стали выбираться по валидации, оба числа на тесте упали:

| | было (выбрано небрежно) | стало (выбрано по валидации) |
|---|---|---|
| Дообученная модель | 0.8318 (эпоха 15) | **0.8102** (эпоха 6) |
| TF-IDF + логрег | 0.7947 (`C=4` наугад) | **0.7939** (`C=8` по валидации) |
| **Разрыв** | **+0.0371** | **+0.0164** |

**Честный разрыв меньше небрежного более чем вдвое.** Старое число 0.8318 не цитировать: 15-я эпоха случайно оказалась удачной на тесте при худшей валидации (0.8119 против 0.8280 у шестой). То же с базовой линией: на валидации `C=8` лучше (0.7997 против 0.7953), на тесте — хуже (0.7939 против 0.7947). Валидация в 2 000 строк шумит, и это шум в обе стороны, а не систематическая ошибка.

*Здесь стоял вывод «выигрыш дообучения над TF-IDF — порядка 0.016 macro-F1». Снят 2026-09-22: замер шума показал, что 0.016 — в пределах разброса по seed, см. «Шум по seed» ниже.* Разрыв по accuracy (0.8472 против 0.8163) тоже считан на одном прогоне и тем же оговоркам подлежит.

**Базовой линии даётся то же усилие, что модели** (`C` по сетке из шести значений на валидации, `--lr` у модели — так же). Иначе сравнение мерило бы не качество подходов, а то, кому из них уделили внимание.

### (d) xlm-roberta-base на MASSIVE ru (2026-09-22)

**Разрыв с TF-IDF на модели побольше вырос: +0.0423 macro-F1 у XLM-R против +0.0163 у tiny2 на том же seed 42 — в 2,6 раза.** Выходит ли он за шум — ниже, в «Шум по seed».

| Подход | macro-F1 | accuracy | lr | Эпоха | Время обучения |
|---|---|---|---|---|---|
| TF-IDF + логрег | 0.7939 | 0.8163 | `C=8` по валидации | — | ~40 с на всю сетку `C` |
| rubert-tiny2, seed 42 | 0.8102 | 0.8472 | 2e-4 | 6 из 15 | 7,5 мин (15 × 30 с) |
| **xlm-roberta-base** | **0.8362** | **0.8702** | 8e-5 | 8 из 8 | **46,2 мин** (8 × 346,5 с) + 86,6 мин подбор lr |

У tiny2 lr подобран не сеткой, а по форме кривой за два прогона (раздел выше). У XLM-R — сеткой 1e-5, 2e-5, 3e-5, 5e-5 по три эпохи на значение и правилом края: лучшим оказался край 5e-5, добавлена проба 8e-5, и она выиграла. Итоги проб по val macro-F1: 0.3106 / 0.5437 / 0.6818 / 0.7277 / **0.7648**.

**Время считано по медиане чистой эпохи, а не по часам.** Настенное время прогона XLM-R — 42 873 с — непригодно: в третьей эпохе пробы 1e-5 машина спала с закрытой крышкой, эпоха заняла 35 082 с. `caffeinate -i` запрещает сон по бездействию, но не закрытие крышки. Медиана 346,5 с по 22 чистым эпохам, от 332 до 392 с. У tiny2 — 30 с по 83 чистым эпохам шести прогонов замера шума; исключены эпоха с ручной паузой (84 с) и шесть эпох прогона seed 46, где машина снова спала. **XLM-R на эпоху медленнее tiny2 в 11,6 раза.**

**ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ: обе выбранные величины XLM-R легли на край, 0.8362 — оценка снизу.** Ни сетку lr, ни бюджет эпох не расширяли, и это сознательное решение ради времени: каждая дополнительная точка сетки — 17 минут проб, каждая дополнительная эпоха — 5,8 минуты, а замер по seed для XLM-R стоил бы около четырёх часов. Числа по XLM-R поэтому нельзя подавать как её потолок; при необходимости уточнять — расширять сетку вверх от 8e-5 и бюджет эпох за 8.
- *lr.* Кривая по lr монотонна во всех пяти точках, оптимум на краю и расширенной сетки. Дальше сетка не расширялась. **Пробы по три эпохи смещают выбор в пользу больших lr, потому что малым нужно больше шагов:** к концу пробы loss у 1e-5 ещё 2.03, у 8e-5 уже 0.49 — проба мерит скорость сходимости, а не качество в точке сходимости.
- *Эпоха.* Валидация выбрала 8-ю из 8, и val macro-F1 к ней ещё рос (0.8423 → 0.8525). Бюджета в 8 эпох, скорее всего, не хватает.

### Шум по seed — замер 2026-09-22

MASSIVE ru + rubert-tiny2, тот же протокол, что у прогона `v2`: lr 2e-4, 15 эпох, выбор эпохи по валидации, базовые линии общие.

| Прогон | seed | Эпоха | macro-F1 | accuracy |
|---|---|---|---|---|
| s42a | 42 | 6 | 0.8102 | 0.8472 |
| s42b | 42 | 6 | 0.8102 | 0.8472 |
| s43 | 43 | 13 | 0.8351 | 0.8469 |
| s44 | 44 | 5 | 0.7984 | 0.8462 |
| s45 | 45 | 8 | 0.8000 | 0.8400 |
| s46 | 46 | 6 | 0.8128 | 0.8490 |

**Разброс по seed** (пять seed, по одному прогону): среднее **0.8113**, min 0.7984, max 0.8351, размах **0.0367**, выборочное ст. откл. **0.0147**.

**Повтор того же seed на MPS** (s42a против s42b): macro-F1 на тесте совпал до последнего знака, **ни одна из 2 913 меток теста не изменилась**, вероятности расходятся не больше чем на 5,3·10⁻³. Недетерминизм MPS при этом есть: train loss расходится с 4-й эпохи в шестом знаке, к 15-й эпохе расхождение доходит до 0.001 в val macro-F1. На выбранной эпохе на итог он не влиял. У XLM-R недетерминизм заметнее: в двух прогонах с одним seed и одним кодом первая эпоха пробы 1e-5 дала val macro-F1 0.1630 и 0.1482. Это одна точка на валидации, на тесте не измерялось.

**Ответ на главный вопрос замера:**
- **tiny2: разрыв с TF-IDF сопоставим с разбросом по seed** — +0.0174 в среднем при ст. откл. 0.0147 и размахе 0.0367, а худший seed обходит TF-IDF всего на 0.0045. **На коротких текстах дообученная tiny2 и TF-IDF неразличимы в пределах шума.** Утверждение «дообучение обходит TF-IDF на коротких текстах» из проекта снято.
- **XLM-R: разрыв +0.0423 выходит за шум tiny2** — это 2,9 его ст. откл. и больше всего размаха. **Но это один прогон, и собственный разброс XLM-R не измерен;** вывод держится на допущении, что шум у неё того же порядка. Пять дополнительных прогонов XLM-R — около четырёх часов.

Две оговорки к этим ответам, обе важны на защите:
1. Все пять seed tiny2 выше TF-IDF. В среднем по seed небольшое преимущество, вероятно, есть; неразличимым оно становится для **одного** обученного экземпляра, а в работу идёт именно один.
2. **XLM-R против tiny2 одним прогоном тоже не различить:** 0.8362 лишь на 0.0011 выше лучшего из пяти seed tiny2 (0.8351). Сказать «многоязычная модель лучше» данные пока не позволяют. Доказано другое, ради чего и был шаг (d): **пайплайн работает с многоязычной моделью без изменений кода.**

### (e) ГРНТИ + rubert-tiny2, длинный вход (2026-09-24)

**На длинных текстах разрыв с TF-IDF не растёт, а меняет знак: tiny2 проигрывает TF-IDF 0.0274 macro-F1**, тогда как на коротких текстах MASSIVE она была впереди на 0.0163 при том же seed.

| Подход | macro-F1 | accuracy | Параметр | Эпоха | Время обучения |
|---|---|---|---|---|---|
| **TF-IDF + логрег** | **0.7264** | **0.7255** | `C=1` по валидации | — | 390 с на всю сетку `C` |
| rubert-tiny2 | 0.6990 | 0.6999 | lr 1e-4 | 3 из 10 | 46,7 мин (10 × 280 с) + 56 мин подбор lr |

Корпус: 28 классов; train 24 204 и validation 4 272 — валидация отрезана от train стратифицированно, потому что у ГРНТИ её нет (исправление в `pipeline.py`, до него прогон падал); test 2 772 не тронут. `max_len 384`: медиана текста 140 токенов, 95-й процентиль 405, целиком помещается 93,7% текстов.

**Относительно шума, измеренного на MASSIVE (ст. откл. 0.0147):** отставание 0.0274 — это **1,9 ст. откл.**, больше одного отклонения, но меньше размаха по seed (0.0367). Прямо: **в шум целиком не укладывается, но и за пределы размаха не выходит** — сказать, что tiny2 на длинных текстах хуже TF-IDF, один прогон не позволяет; сказать, что лучше или не хуже, — тем более. Шум мерился на другом корпусе, это допущение.

**Вывод устойчив к выбору эпохи и lr.** На валидации TF-IDF даёт 0.7369, а лучшее, что tiny2 получила в любой конфигурации, — 0.7221 (проба lr 1e-4 за три эпохи). Самая выгодная для модели цифра ниже базовой линии.

**Известное ограничение: финал хуже собственной пробы.** Финальный прогон с тем же lr на 10 эпохах дал на валидации максимум 0.7074 против 0.7221 у трёхэпохальной пробы. При линейном затухании на 10 эпох шаг к 3-й эпохе ещё велик, а с 4-й модель переобучается: train loss 0.38 → 0.005, val падает до 0.688. Значит, 0.6990 занижает возможности tiny2 на ГРНТИ — но и выгодная конфигурация TF-IDF не обходит. Бюджет эпох под длинный вход не подбирался.

**Асимметрия входа:** tiny2 видит первые 384 токена, TF-IDF — весь текст. Какую долю разрыва это объясняет, не измерялось.

**lr выбран внутри сетки, а не на краю** — 5e-5 → 0.7038, **1e-4 → 0.7221**, 2e-4 → 0.7163, 4e-4 → 0.7042; правило края не сработало. В отличие от XLM-R, здесь подбор lr честный.

**Время** — по медиане 16 чистых эпох, 280 с. Исключены 6 эпох, во время которых машина спала с закрытой крышкой (от 897 до 44 242 с); настенное время прогона 122 576 с непригодно.

| Шаг | Что доказано | Чего **не** доказано |
|---|---|---|
| a, b | пайплайн обучается; перемешанные метки роняют macro-F1 до случайного уровня (0.0151 при 0.0169) — утечки нет | — |
| c | базовые линии считаются с тем же усилием, что модель | — |
| d | пайплайн работает с многоязычной моделью без правок кода | что многоязычная модель лучше: от tiny2 одним прогоном не отличить |
| e | длинный вход не ломает пайплайн | что дообучение на длинных текстах выгоднее TF-IDF: на ГРНТИ наоборот |
| шум | прогоны совпадают в пределах измеренного шума, ст. откл. 0.0147 | — |

**Дообучение маленькой модели не обходит TF-IDF ни на коротких текстах, ни на длинных.** Выход за шум показала только XLM-R на коротких, и то одним прогоном. Для модуля 1 это значит: когда придёт текст обращений, TF-IDF + логрег — не заглушка, а сильная базовая линия, которую дообучение обязано обойти на тех же данных, прежде чем идти в работу.

### Что изменится, когда придёт настоящий текст

Не меняется: контракт CSV и флаги колонок, дедупликация, кодировщик меток, цикл обучения, набор метрик и базовых линий, проверка перемешиванием, формат артефактов, `predict`.

Меняется: режим разбиения на `temporal`; базовая модель, если текст двуязычный — русская на казахском бесполезна; политика редких классов под 15 тем вместо 60 интентов, причём «прочее» уже существует как класс и сливать в него ещё что-то нельзя; печать примеров в `report.md` — текст обращения содержит ПДн по умолчанию и выводится только маскированным (раздел 1).

## 5l. Модуль 2 — дообученные эмбеддинги для поиска похожих: постановка (утверждена 2026-09-24)

**Зафиксировано в git ДО кода** — основная метрика и правило решения ниже не меняются после прогонов. Приём тот же, что со списком вопросов NLQ (раздел 5h): иначе метрику и порог можно подобрать под то, что получилось.

**Задача.** По тексту обращения найти k похожих **ранее поступивших**. Индекс — только прошлое, запрос в свой индекс не входит. На этапе отладки «похоже» = совпадение метки корпуса.

### Корпус и две проблемы прокси

MASSIVE ru, тот же, что в модуле 1: после чистки train 10 734 текста, 59 классов, от 796 (`calendar_set`, 7,4%) до 14 на класс. Почти-дублей между train и test нет: после нормализации регистра и замены цифр — 0 из 2 913 запросов; точные дубли снимает `dedupe` модуля 1.

1. **При «похоже = та же метка» поиск сводится к классификации.** Высокий результат докажет, что пайплайн работает, но не решает настоящую задачу модуля 2 — найти **ту же проблему**, а не ту же тему.
2. **Сравнение с базовыми линиями перекошено по построению.** Дообученная модель учится на тех же метках, по которым её оценивают; TF-IDF и готовые эмбеддинги меток не видят. Поэтому введена **опора на метках** — базовая линия, которая метки тоже видит. **Сравнение с ней — главное.**

### Модель

**`intfloat/multilingual-e5-small`**: MIT, русский и казахский в языках карточки, 12 слоёв × 384, словарь 250 037, до 512 токенов, около 118 млн параметров, из них ~96 млн — матрица словаря. Обучена как эмбеддинг-модель, поэтому её версия без дообучения — честная базовая линия.

- **Префикс сверен с карточкой 2026-09-24:** для симметричных задач — `query: ` на обеих сторонах, без префикса качество падает. Mean pooling, нормировка, косинус.
- **Матрица словаря при дообучении заморожена по умолчанию:** обучаемых параметров впятеро меньше, и эмбеддинги казахских токенов не сдвигаются при обучении на русском. Флаг — разморозить.
- Не взяты: `paraphrase-multilingual-MiniLM-L12-v2` (нет казахского), `rubert-tiny2` (только русский), `bge-m3` (568 млн, тяжела для MPS в fp32), `multilingual-e5-base` (вторая точка кривой, только если small даст выигрыш).

### Обучение

**Supervised contrastive на батчах P классов × K примеров** (16 × 4). Все тексты той же метки в батче — положительные. Не MultipleNegativesRanking: при батче 32 у крупнейшего класса вероятность второго своего примера в батче ≈ 0,91, у типичного ≈ 0,41 — массовые ложные отрицательные. **Выборка P × K снимает вырождение пар:** из 1 810 657 пар внутри классов 17,5% приходится на один `calendar_set`, у мельчайшего класса их 91; P × K берёт каждый класс с равной вероятностью независимо от размера.

Протокол модуля 1: lr сеткой по валидации с правилом края, эпоха по валидации. Свой цикл, без `sentence-transformers` (не установлена, совместимость с transformers 5.17 не проверена). Разбор данных переиспользуется из `src/finetune/pipeline.py`.

### Метрики — зафиксированы

- **Основная: macro precision@10** — из 10 найденных доля той же метки, усреднение по классам запроса.
- Справочно: precision@1, hit@10 (есть ли в топ-10 хоть один той же метки).
- `recall@k` в буквальном смысле не считается: при 796 примерах класса в индексе recall@10 ≤ 0,013 даже у идеальной модели.
- Случайный уровень печатается: macro 1/59 ≈ 0,0169, по запросам Σp² = 0,0315.
- **Без утечки:** индекс — train, запросы — test; тест не входит ни в индекс, ни в обучение. Выбор lr и эпохи — по запросам из валидации против train-индекса.

### Базовые линии — четыре

1. TF-IDF (слова + символьные n-граммы, как в модуле 1), косинус.
2. **e5-small без дообучения** — тот же энкодер до обучения; разница с ним — чистый эффект дообучения.
3. **Опора на метках:** вероятности классов TF-IDF + логрега (модуль 1, `C` по валидации) как вектор, косинус.
4. Справочно: rubert-tiny2 без дообучения.

### Правило решения — три условия, зафиксировано

Дообучение **обходит** базовую линию, только если выполнены все три условия:

1. среднее macro precision@10 по пяти seed выше базовой линии больше чем на **два** стандартных отклонения разброса по seed;
2. **худший** seed тоже выше базовой линии;
3. 95% интервал **парного бутстрэпа** по тем же запросам теста (1 000 повторов) для разности «дообученная модель seed 42 − базовая линия» не содержит нуля.

Иначе — «**неразличимы в пределах шума**». Правило применяется к **обоим** сравнениям: против e5 без дообучения и против опоры на метках. У базовых линий разброса по seed нет, их неопределённость — только бутстрэп.

### Порядок работ

1. Базовые линии, все четыре. 2. Подбор lr с правилом края, выбор эпохи по валидации. 3. Финал, одна модель. 4. Замер шума: 5 seed плюс парный бутстрэп. 5. Правило трёх условий к обоим сравнениям.

Отчёт начинается двумя фразами: обошло ли дообучение готовые эмбеддинги и обошло ли опору на метках; **второе важнее**.

### Артефакты

`models/embed/<прогон>/` (не коммитится): веса, токенизатор, `embed_config.json`, `run.json`, индекс эмбеддингов, `neighbours.csv`. `reports/embed/<прогон>/` (коммитится): `metrics.json`, `report.md`. **Эмбеддинги — построчный артефакт** и на реальных обращениях считаются содержащими ПДн: по эмбеддингу текст частично восстановим. Индекс хранит отпечаток модели и отказывает запросам от другой модели.

### Результат (2026-09-24)

**Дообучение обошло готовые эмбеддинги: +0.2063 macro precision@10 к e5 без дообучения, все три условия правила выполнены.**
**Дообучение обошло и опору на метках: +0.0478 к 0.7780, все три условия выполнены — это главное сравнение, и оно пройдено.**

### Обмен точности на охват

**По основной метрике дообучение выигрывает, по справочной — проигрывает, и на всех пяти seed в одну сторону.**

| | e5 без дообучения | Опора на метках | **Дообученная e5, пять seed** |
|---|---|---|---|
| macro precision@10 — все десять соседей по делу | 0.6195 | 0.7780 | **0.8259** (0.8178–0.8346) |
| macro hit@10 — хоть один сосед по делу | **0.9319** | 0.8150 | 0.8541–0.8724 |

**Обучение на метках сдвигает модель к классификатору.** Соседи становятся однородными: либо все десять той же метки, либо — если метка угадана неверно — все десять чужие. Готовая e5 раскладывает соседей шире, и хотя бы один подходящий среди них находится чаще. **Для оператора, которому нужен один прецедент, это ухудшение:** hit@10 падает с 0.932 до 0.854–0.872. Для оператора, которому нужна подборка «все десять по делу», это улучшение. Правило решения зафиксировано на precision@10 до прогонов, поэтому вердикт «обходит» стоит; обмен называть на защите вслух и выбирать режим по сценарию работы оператора. Бутстрэп для hit@10 не считался — величины по запросам сохранены только для precision@10; вывод держится на том, что знак разницы одинаков на всех пяти seed.

### Победа на прокси, а не на задаче

**Доказана группировка по метке интента, а не поиск той же проблемы.** Для настоящей оценки модуля 2 нужен адрес или ключ заявителя — раздел 10, пункты 9–10.

### Известные ограничения

- **Эпоха на краю у 4 seed из 5:** выбрана последняя, 10-я эпоха, валидация к ней ещё росла. **0.8259 — оценка снизу.** На вердикт не влияет: занижение работает против дообучения.
- **Недетерминизм MPS у контрастивного обучения заметнее, чем у классификатора.** Прерванный и перезапущенный прогон одного seed (42, тот же код) совпали на эпохах 2–3 (val 0.7907 / 0.7908, 0.8242 / 0.8240) и разошлись к эпохе 7 на **0.017 по валидации** (0.8341 / 0.8168) — это 2,5 ст. откл. разброса по seed. У классификатора в модуле 1 повтор seed не менял ни одной метки теста. На вердикт не влияет: худший seed обходит опору на 0.040, интервал бутстрэпа отстоит от нуля на 0.027.
- **Лог прерванного прогона утерян:** ad hoc-цепочка писала в имя без метки времени, и перезапуск его затёр; числа выше сохранились только в записи сессии. **Исправлено:** цепочка перенесена в `scripts/embed_chain.sh`, имя каждого лога содержит метку времени запуска прогона, перезапуск пишет в новый файл. Попутно закрыта соседняя ловушка того же рода: правило трёх условий раньше собирало прогоны по маске, и при повторном запуске в него попали бы старые прогоны тех же seed (`decide.py` упал бы на проверке повтора seed, но цепочка сломалась бы). Теперь цепочка передаёт в `decide.py` ровно те `metrics.json`, которые создала сама.

### Что изменится на реальных обращениях

Не меняется: контракт и флаги, дедупликация, разбиение, потеря и выборка P × K, метрики, артефакты, правило шума. Меняется: **определение похожего** (нужна «та же проблема», а для неё — адрес или ключ заявителя, раздел 10, пункты 9–10, либо пары, размеченные людьми); индекс становится причинным по времени (`--time-col`); модель пересматривается, если тексты казахские; индекс и соседи хранятся по правилам раздела 1.

## 5m. Подсказка типового ответа оператору — исследована и НЕ строится (2026-09-24)

**Решение: подсказку типового ответа не строим. Это результат исследования, а не отложенная задача.** Проверено, на чём её можно было бы построить, и в выгрузке этого нет.

Задумка была такая: по теме, региону и службе предложить оператору типовую формулировку ответа — из того, что исполнители раньше писали по похожим обращениям. Текст ответа есть только в колонках, которые в канон не переносятся (раздел 5c), поэтому считалось по региональным файлам после той же чистки, что в адаптерах: дедупликация и отсев сдвига полей. Разведка разовая, скрипт в `analysis/answers/` (вне git). Значения текста не выводились — только агрегаты (раздел 1).

### 1. Охват — один регион из семи

| Регион | Колонка ответа | Заполнено | Доля обращений региона, которым можно было бы показать подсказку |
|---|---|---|---|
| **Костанай** | `result` | 100% (20 591) | **32,6%** |
| Алматы | `com_exp` | 30,1% (5 818) | 3,7% |
| ВКО | `com_exp` | 2,0% (1 687) | 0,2% |
| Туркестан, Караганда, Акмола, Павлодар | **колонки ответа нет** | — | 0% |

`result` у ВКО и Алматы — не текст ответа, а справочник из **4 значений** (статусы). У Туркестана колонки `result` в выгрузке нет, хотя система у него общая с Костанаем — вопрос заказчику, раздел 10, пункт 14.

### 2. Безопасный белый список — это поле статуса, а не ответ

Отбор: нормализация (регистр, пробелы, крайняя пунктуация) → частота не меньше k\* → число разных исполнителей не меньше m\* → ни одного срабатывания шаблонов ПДн → ручной просмотр. Оба порога **выведены из данных, а не назначены**:

- **k\*** — наибольшая частота формулировки, на которой сработал хоть один шаблон, плюс один: выше k\* срабатываний в данных нет. Костанай 84, Алматы 27, ВКО 2.
- **m\*** — наибольшее число исполнителей у формулировки с флагом, плюс один: иначе формулировка может быть подписью одной организации. Костанай 4, Алматы 2, ВКО 2.

| | Костанай | Алматы | ВКО |
|---|---|---|---|
| Формулировок в белом списке | **8** | 6 | 10 |
| Медианная длина | **9 символов** | 12 | 18 |
| Покрытие непустых ответов | 32,6% | 12,2% | 9,0% |

**Восемь формулировок медианной длиной 9 символов — это одно-два слова, по информативности поле статуса, а не ответ.** Всё, что длиннее и содержательнее, отсеялось как содержащее или способное содержать ПДн.

### 3. В большинстве случаев подсказка была бы пустой

В ячейках «тема × служба» Костаная, где не меньше 20 ответов, **медианная доля ответов из белого списка — 15%**. Для большинства обращений подходящей формулировки в ячейке нет, и подсказка свелась бы к «типового ответа нет».

### 4. Гипотеза «частое значит безопасное» опровергнута на данных

Частота защищает от ПДн **заявителя**, но не от ПДн **исполнителя** — подписи или контакта, которые вставляются в каждый его ответ.

- У Костаная формулировка с **83 повторами** даёт срабатывание адресного шаблона и слово с фамильным окончанием, используют её **два** исполнителя; с **77 повторами** — фамильное окончание, **один** исполнитель. То, что это подписи или контакты исполнителей, — вывод из флагов и числа исполнителей, а не из прочтения: текст не выводился.
- **Доля срабатываний шаблонов с частотой не убывает:** при 5–9 повторах 0,8% формулировок (телефон, 12 цифр, адрес), при 50–99 — **7,7%**. Чистым у Костаная оказался только разряд от 100 повторов.

Поэтому одного порога частоты недостаточно — понадобился второй, по числу исполнителей, и ручной просмотр для имён, которые шаблоны по цифрам не ловят.

### 5. Содержательное возражение: заглядывание в будущее

**Ответ исполнителя пишется после работы.** Показать его оператору при приёме обращения значит пообещать гражданину исход («выполнено»), которого ещё нет. Здесь это не гипотеза, а свойство самой колонки: текст результата появляется после обработки по определению. У `answer_type` в модели просрочки тот же вопрос остаётся открытым — момент его простановки не проверен (раздел 9). Уместное место такой подсказки — **закрытие обращения**, когда результат уже известен, а не приём.

### 6. Вывод

**Подсказка типового ответа требует текста обращения и структурированных ответов, которых в выгрузке нет.** Это ограничение данных, а не реализации, и оно стоит в одном ряду с двумя уже зафиксированными:

- **дубликаты по каноническим метаданным не выявляются** — нужен ключ заявителя (раздел 5j, раздел 10, пункт 9);
- **внешнего корпуса обращений граждан с текстом не существует** ни на одном языке (раздел 5k).

Полезность подсказки, будь она построена, измерить сейчас тоже было бы нечем: журналов работы операторов нет. Измерима была бы только предсказуемость формулировок исполнителей — а это не то же самое, что польза оператору.

### Маппинг тем сравнивает подстроки, а не слова — к октябрю

`src/topic_mapping.py` проверяет вхождение ключа как подстроки в название темы. Ключ срабатывает внутри слов, где он оказался случайно. Уже случилось:

| Ключ | Где сработал случайно | Строк | Куда ушло вместо нужного |
|---|---|---|---|
| `провод` | «Прорыв трубо**провод**а» | 428 | электроснабжение вместо воды |
| `опор` | «Прав**опор**ядок» | 2 042 | электроснабжение вместо безопасности |

Живые примеры, найденные повторным аудитом 2026-09-11 и закрытые сужением ключа (см. 5e):

| Ключ | Где сработал случайно | Строк | Куда уходило вместо нужного |
|---|---|---|---|
| `провод` | «…перемонтаж газо**провод**а» | 9 (Караганда) | электроснабжение вместо ЖКХ |
| `провод` | «интернет (**провод**ной, бес**провод**ной)» | 3 (Акмола) | электроснабжение вместо связи |
| `провод` | «путе**провод**» | 0 сейчас | правило «дороги» с ключом `путепровод` было недостижимо |

Все случаи сейчас закрыты заплатками — порядком правил, ключами `трубопровод`/`газопровод` и маркером начала слова `^`, — а не устранены по существу. **На новых регионах с другими словарями это повторится.** Регресс-тест ловит переезды только между прогонами одного набора данных; новый регион приходит без эталона, и первую ошибку тест не увидит.

**Решение к октябрю:** нормализация (нижний регистр, `ё`→`е`, приведение к основе или лемме) и сравнение по целым словам вместо подстрок.

**Чего это решение не закроет — отдельный класс ошибок.** «Запах газа» (42 строки уходили в санитарию по ключу `запах`) — это не случайная подстрока: «запах» там целое слово, просто в контексте, где тема определяется всей фразой. Сравнение по словам его не исправит. Для таких случаев нужны правила на фразах с приоритетом над одиночными словами — сейчас эту роль играет раннее узкое правило газа. То же относится к многословным ключам с окончаниями между основами («уборк улиц» против «уборка улицы»): их закрывает нормализация, но не сравнение по словам само по себе.

**Скрытая мина: `norm()` срезает граничные пробелы и в ключах.** Ключи `"газа "` (ЖКХ) и `"выбор "` (класс `info`) задумывались как «слово до пробела», но `strip()` превращал их в голые подстроки. Сейчас вреда нет: у `"газа "` затронутых строк 0, а все 2 944 строки «Выборы…» и так ловит отдельный ключ `"выборы"`. Любой новый ключ с граничным пробелом будет молча работать иначе, чем написан. Для тем обходится маркером `^` в `_match()`; для классов обращения (`classify_appeal`) не исправлено.

**Целое слово в чужом контексте.** Акмола, 1 строка: «Вопросы по внутренней отделке помещения на МЖД… (плитка, штукатурка, места проводов…)» уходит в электроснабжение по слову «проводов», хотя по смыслу это жилищный фонд. Тот же класс, что «запах газа»: сужение ключа или сравнение по словам не помогут, нужны правила на фразах.

   **Вывод для отчётности: сравнение ВКО по темам через 2023 год требует проверки по каждой теме отдельно** — общего «до и после» у региона нет. Просим подтвердить, что именно менялось: справочник категорий, практика регистрации или система-источник, и по каким темам и датам (раздел 5g).
9. **Как передавать признак заявителя для выявления повторных обращений?** Сейчас повторы не выявляются: по каноническим метаданным они неразличимы — у Павлодарской области заполнено пять полей из восьми, и они совпадают у тысяч обращений (раздел 5j). Нужен адрес обращения или идентификатор заявителя, но это персональные данные, и в исходном виде мы их не принимаем. **Просим предложить приемлемую форму:** устойчивый хеш от номера телефона или ИИН, обезличенный сквозной ключ заявителя, либо адрес, огрублённый до дома без квартиры. Нам достаточно, чтобы одинаковые заявители совпадали между строками — восстанавливать личность не требуется.
10. **Район: у Костаная одно значение на всю область, у двух регионов поля нет вовсе.** `district` у Костанайской области заполнен на 100%, но содержит единственное значение — «КОСТАНАЙ». Формально поле полное, фактически разреза нет.

   | Регион | Заполнено | Уникальных значений |
   |---|---|---|
   | Карагандинская | 100% | **34** |
   | Восточно-Казахстанская | 0,86% (718 из 83 382) | 25 |
   | Акмолинская | 93,12% (3 235 из 3 474) | 19 |
   | Туркестанская | 100% | 17 |

   | Алматинская | **0,00%** | 0 |

   Пригодный разрез по районам есть только у Караганды и Туркестана. У ВКО значения содержательные (посёлки и районы), но заполнены меньше чем в 1% строк. У Павлодара и Алматы — крупнейшего и одного из самых свежих регионов — поля нет совсем.

   **Что из-за этого невозможно.** Во-первых, локализовать событие внутри региона: детектор показывает всплеск по области целиком, и куда направлять бригаду — из данных не следует. Во-вторых, выявлять повторные обращения по одному адресу: без района не работает даже грубое сопоставление (см. пункт 9 и раздел 5j).

   **Просим выгружать район или населённый пункт фактическим значением** — для всех регионов, а не только там, где поле уже заполнено. Для Костаная это означает район города, а не название области.

14. **Туркестанская область: в выгрузке нет колонки `result` — текста результата обработки.** У Костаная, выгруженного из той же системы (38 общих категорий, раздел 5c), эта колонка есть и заполнена на 100%; у Туркестана это единственная колонка, которой его 24 колонки отличаются от 25 у Костаная.
