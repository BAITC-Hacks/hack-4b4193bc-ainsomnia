## Проекты следующих решений

**Action Queue:** NEW_SPIKE — только существующая секция новых событий относительно конца каждого региона; SLA_RISK — историческая проверочная очередь Караганды с подписью периода; DATA_QUALITY — причина из Health; DATA_STALE — только после согласования ожидаемой даты/частоты; FORECAST_CHANGE — только при двух сопоставимых сохранённых прогнозах с одинаковым горизонтом. BLOCKED качества → CRITICAL; прочие предупреждения/всплески → HIGH; историческая очередь риска → NORMAL. Между типами нет арифметического score. Поля: stable ID, type, priority_reason, region, topic, date, headline, evidence, recommended_next_check, source_module. Нет предпосылок — нет выдуманной строки.

**Risk explanations:** после отдельной постановки восстановить ровно тот preprocessing сохранённой логрегрессии, проверить `intercept + sum(x_j * coef_j) == decision_function` с допуском 1e-10, а sigmoid — predict_proba. Показывать 2–3 положительных вклада, если они есть; текст «признаки, повысившие оценку модели». Поля и значения проходят маскирование. Не причинность, не SHAP.

**Capacity:** существующий forecast считает жалобы класса problem, не все контакты. До появления прогноза всех контактов выход называется «прогноз жалоб» и сценарий покрывает только этот поток. Ёмкость = операторы × часы × 60 / минуты × (1 − резерв/100); пользователь задаёт горизонт и смены в том же периоде, что спрос. Нижний/базовый/верхний сценарий 0.8/1/1.2 — допущение, не доверительный интервал. Это не рекомендация штата.

**Recurrence:** следующий старт всплеска той же пары регион×тема в (end, end+7/30/60]; при недонаблюдённом горизонте — UNKNOWN, не false. Пропуски тоже цензурируют наблюдение. Жалобы до возврата к фиксированному фону считать по существующему дневному ряду; если возврат не наблюдался — цензурированный итог. Не идентификация аварии.

**Closure:** использовать итог после noise checks из `reports/5o/signals.md`, а не предварительную применимость. VERIFIABLE требует все нужные поля и достаточные наблюдения с пройденными проверками; PARTIAL — только перечисленные проверяемые стороны; NOT OBSERVABLE — отсутствует независимая проверка решения. В нынешнем 5o ноль триангулированных сигналов, нет основания объявить полную проверяемость. Исполнитель, факт закрытия, незакрытые записи, объём и noise — отдельные колонки. Не рейтинг служб.

**Feedback:** отложен до auth. Анонимная запись создала бы ложное ощущение проверяемого аудита. Затем SQLite вне git, enum-метки из задания, UTC timestamp, стабильный ID из source+dataset+region+topic+start, structured note только из разрешённых полей. Автообучения нет.

**Brief:** deterministic HTML и существующий PDF-стек из одного объекта агрегатов; generated_at и data_as_of по регионам. Семь разделов задания, отсутствие данных явно. Числа повторяются из очереди, риска и прогноза, повторных моделей нет.

**API decision:** отложить до появления интеграционного потребителя и auth. Стандартный `http.server` годится для локального smoke, но не заменяет production auth, маршрутизацию, лимиты и контракт ошибок. FastAPI добавляет зависимость и отдельный обслуживаемый сервис; пока дублировал бы Streamlit без заказчика. Будущий read-only контракт: /health, /data-quality, /alerts, /forecast, /metadata; только агрегаты и те же ограничения регионов. Новых зависимостей сейчас нет.

**Auth/logging:** viewer — просмотр; analyst — просмотр/export/feedback; admin — build/configuration. Роль и разрешённые регионы получаются из проверенного identity, неизвестная роль/пустой scope — отказ, не все регионы. Требуются issuer/client/redirect/claim mapping и secret store заказчика; значения не придумываются. До подключения только private. После auth JSON stdout: event, timestamp, result, dataset_id, region scope, row_count; actor — внутренний псевдоним, согласованный с заказчиком, не email/ФИО/token. События dashboard_open/filter_change/export_excel/export_pdf/feedback_submit/data_build/build_failure. Содержимое жалоб и exception payload не журналируются.

**Atomic refresh — проект, пока не реализован:** отдельная эксклюзивная build-блокировка → неизменяемая копия/снимок принятого сырья → `releases/<uuid>.tmp` на том же томе → manifest/schema → adapters → labeling → Health → spikes → forecast → проверка ПДн и fingerprint результатов → fsync → rename завершённого каталога → atomic replace указателя `current`. Читатель закрепляет один release на весь запрос; не читает data из нового, а reports из старого. Указатель переключается только после всех проверок; при сбое старая версия остаётся, failure metadata отдельно. Падение после rename, но до pointer swap, оставляет неактивный готовый release. GC/удаление — только по будущему retention. Risk train отдельной явной командой, его dataset_id проверяется при чтении. Настоящий `NAZAR_WORK_DIR` не открывать как обход изоляции: staging — внутренний объект pipeline с теми же source checks. До реализации и failure injection текущая сборка НЕ атомарна. Scheduler зависит от канала и частоты заказчика.

**Security gaps:** auth/public exposure — blocker; compose loopback закрывает только default Compose. Шифрование диска, backup, retention, юридическое основание и S3 policy — external. Секреты только будущий secret store, не git/env в образе. Права raw проверяются отдельно и не меняются молча; PII scanner не доказывает безопасность произвольного свободного текста.
