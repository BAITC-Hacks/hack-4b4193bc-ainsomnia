# Backup и restore

Это инструкция, не настроенное резервирование. Retention, RPO/RTO, шифрование, площадка и ответственный — EXTERNAL. В git не помещаются ни backups, ни raw, ни parquet, ни модели, ни predictions.

Резервировать только завершённый неизменяемый release: `metadata.json`, `manifest/`, `data/`, нужные dashboard `reports/` и явно перенесённые `models/`, плюс CURRENT как справочную запись и конфигурацию без секретов. При наличии predictions/data считать backup содержащим ПДн, даже если отчёты агрегатные. Фильтры UI не обезличивают диск.

`runtime/inputs/` содержит снимки исходного сырья и НЕ включается автоматически. Building/failed релизы и логи — только по отдельной политике, не вместо последнего принятого backup. Секреты OIDC/S3/SSH не включаются в обычный архив приложения; их восстановление — процесс secret store заказчика.

Имя: `nazar-109/<source>/<release-id>/<UTC-date>/release.tar` и `release.tar.sha256`. Перед копированием записать ID из CURRENT, использовать ровно этот каталог; смена CURRENT не меняет его содержимое. Сохранить SHA256 архива и hashes артефактов из metadata. Передача по проверенному каналу; checksum обнаруживает порчу, но сам по себе не аутентифицирует отправителя — ожидаемый checksum нужен из доверенного каталога backup.

Restore:

1. Выбрать разрешённый backup и подходящую версию кода; не перезаписывать живой runtime.
2. Проверить checksum и список архива до распаковки: запрет absolute paths, `..`, symlink и hardlink наружу. Распаковать в отдельный пустой runtime нужного source с владельцем/правами сервиса.
3. Восстановить SOURCE и `releases/<id>`, не делать CURRENT из непроверенного архива активным автоматически.
4. `nazar-rollback --release <id>` выполняет полную проверку artifacts/hash/source/mapping до переключения; при отказе восстановленный набор не публикуется.
5. `nazar-health` должен вернуть ready; выполнить AppTest/просмотр пяти вкладок и пробные экспорты. Перезапустить dashboard для выбранной версии. До разрешения доступа не открывать наружу.

Rollback использует уже сохранённый локальный READY release, без переноса данных. Restore возвращает утраченные файлы из backup и только затем допускает переключение. Автоматического удаления релизов/inputs/backups нет. Для GC нужны срок хранения, согласование владельца, проверка ссылок CURRENT/backup и отдельная операция. Периодический restore drill должен стать эксплуатационной проверкой после выбора хранилища.
