# NAZAR-109

Платформа аналитики обращений в единый контакт-центр 109. Настоящая объединённая таблица содержит **988 776 строк по семи регионам Казахстана**. Система различает жалобы на городские проблемы, справочные звонки и служебные записи; для жалоб используется **15 тем**, включая «прочее».

Витрина на **Streamlit** объединяет очередь действий, качество данных, планирование нагрузки и риск просрочки только для Караганды. Отдельные команды строят прогноз нагрузки и отвечают на вопросы к структурированным данным. Выгрузка — Excel и PDF. Подробные решения и ограничения находятся в [CLAUDE.md](CLAUDE.md).

**REAL** — рабочая система на разрешённых структурированных данных заказчика. **FAKE** — технический integration test: искусственная выгрузка проверяет тот же конвейер и CI, её модель и результаты не используются в рабочем real-режиме.

## Быстрый старт без настоящих данных

Нужны macOS или Linux, **Python 3.12**, Git и установленный `uv`. Основное окружение занимает ориентировочно 2 ГБ; `requirements-ml.txt` для этого запуска не нужен. Команды выполняются из корня репозитория.

```bash
git clone https://github.com/arlmango/NAZAR-109.git
cd NAZAR-109
uv venv .venv
uv pip install --python .venv/bin/python -r requirements.lock --require-hashes
uv pip install --python .venv/bin/python --no-deps -e .
export NAZAR_SOURCE=fake
.venv/bin/nazar-build-data
.venv/bin/python train.py
.venv/bin/nazar-dashboard
```

Откройте `http://localhost:8501`. Это **ПОДДЕЛЬНЫЕ ДАННЫЕ**: числа не описывают реальные обращения и не являются результатами регионов Казахстана. Метрики обученной на них модели служат только проверкой конвейера.

Результаты появляются в `fake_run/data/`, `fake_run/reports/`, `fake_run/models/`, вне git. Настоящие результаты в корневых `data/` и `reports/` не перезаписываются. Для другого каталога результатов можно задать `NAZAR_WORK_DIR`, в том числе вне репозитория; эта переменная разрешена только в режиме `fake`.

Ожидаемый результат:

| Проверка | Значение |
|---|---:|
| Строк в объединённой таблице | 12 910 |
| Жалобы (`problem`) | 8 266 |
| Справка (`info`) | 3 661 |
| Служебные записи (`system`) | 983 |
| Заложенные всплески | 1 |

Единственный всплеск — Костанай, благоустройство и озеленение, 27.08.2025: 40 жалоб при обычном уровне 1. Витрина показывает восемь блоков: что сейчас важно, всплески, риск просрочки, состав потока, темы жалоб, динамику по месяцам, общие цифры и выгрузку отчётов. Сверху находится плашка поддельных данных.

**Время:** в локальном аудите 27.09.2026 на macOS, Python 3.12.13, уже установленное окружение, сквозной тест занял 13,95 с. Это регенерация набора, сборка, обучение, проверка витрины через AppTest и отрицательный сценарий; установка зависимостей и время открытия браузера сюда не входят. Это измерение конкретного прогона, не обещание времени на другой машине.

## Локальная подготовка к deployment: P3

Новый release mode включается явно и не меняет прежний quick start:

```bash
export NAZAR_SOURCE=fake
export NAZAR_RUNTIME_DIR="$PWD/runtime/fake"
.venv/bin/nazar-refresh
.venv/bin/nazar-health
.venv/bin/nazar-dashboard
```

Refresh собирает отдельную версию и переключает `CURRENT` только после обязательных проверок. При отказе рабочий релиз сохраняется. Риск автоматически не обучается. `nazar-rollback --release ID` проверяет и выбирает прежний READY release без пересборки. Данные и снимки сырья в `runtime/` не коммитятся и не удаляются автоматически.

Витрина закрепляет версию при запуске и показывает её ID. После refresh/rollback нужен явный перезапуск процесса; `nazar-health` проверяет CURRENT, а Streamlit health endpoint — только liveness. Логи операций — JSONL без строк обращений.

[Runbook](docs/deployment.md), [приёмка P3](docs/p3-results.md), [backup/restore](docs/backup.md), [S3 contract](docs/s3.md) и [внешние решения](docs/deployment-external.md). Подготовлены [release compose](deploy/compose.release.yml) и [пример Caddy](deploy/Caddyfile.example). Полный контейнерный запуск и PDF в Docker ещё не проверены; REAL требует согласованных доступа, OIDC, шифрования, retention и правового основания. Никакого push/deploy в P3 не выполнялось.

## Операционный слой P2

Первая таблица — **«Что требует внимания»**: новые всплески, историческая очередь риска Караганды, предупреждения Data Health и сезонный переход прогноза. Приоритеты BLOCKED/HIGH/WATCH заданы правилами, общего AI score нет. Новизна — последние 7 дней данных своего региона, не сегодня; всплески упорядочены по абсолютному приросту.

Далее пять вкладок:

- **Оперативно:** качество, прежняя лента и риск. Для выбранной позиции риска показаны до трёх положительных вкладов модели; это ассоциации в logit, не причины просрочки.
- **Планирование:** прогноз на 13 недель от конца данных; ручной сценарий мощности и ±20% входящего потока; повторное давление темы с ненаблюдаемыми окнами 7/30/60 дней. Часы вводятся на оператора за весь горизонт, не за день. На FAKE рабочий прогноз не применяется.
- **Контроль качества:** карта 5o «Можно ли проверить факт решения?» и структура потока. Карта привязана к проверенной REAL-версии; не рейтинг служб.
- **Аналитика:** темы, месяцы и общие числа с прежними фильтрами.
- **Отчёты:** deterministic оперативная сводка HTML/PDF без LLM и прежние Excel/PDF. Сводка охватывает все регионы; старые выгрузки учитывают фильтры аналитики.

Текущий REAL после принятого mapping: **1 225 всплесков**, 302 строки сменили тему, число обращений и классы сохранились. [Полный diff и пересчёт](docs/topic-mapping-results.md). [Приёмка P2](docs/p2-results.md) содержит проверки, числа и ограничения. Полный REAL не хранится в репозитории; FAKE проверяет программный путь, а не качество модели.

[Внутренний service-layer](docs/service-layer.md) вызывается без Streamlit. [Feedback](docs/feedback.md) отложен до [OIDC](docs/auth.md); HTTP API не добавлен. [Atomic refresh](docs/atomic-refresh.md) реализован отдельной opt-in командой `nazar-refresh`; legacy build остаётся неатомарным. Публичный deployment до приёмки доступа и обновления не разрешён. Постановки P2.1–P2.6 — в [CLAUDE.md](CLAUDE.md).

## Качество и свежесть данных

После `nazar-build-data` витрина показывает девятый раздел — «Качество и свежесть данных»: окно каждого региона, пропуски, заполненность полей, состав обращений, новые категории и фактический отсев. Статусы OK / WARNING / BLOCKED имеют конкретные причины, общего балла качества нет. Повреждённый канон, несовпадение профиля или неуспешная сборка блокируют аналитические секции.

Первый профиль честно показывает отсутствие предыдущей успешной версии. После принятия и сборки новой выгрузки доступны изменения строк, категорий, долей классов/тем, полноты и окна. Повтор той же версии сохраняет сравнение с предыдущей отличающейся версией. Дата сборки отделена от даты данных; историческая Караганда, пропуск Туркестана и смена состава ВКО видны явно. Частота обновления заказчиком пока не задана.

Профили `data/data_health.json`, `data/data_health_previous.json`, счётчики и состояние сборки — локальные агрегаты вне git. Пороги и приёмка зафиксированы в [CLAUDE.md, 0e](CLAUDE.md#0e-операционный-центр-109--границы-и-план-2026-09-27). [Актуальный backlog](docs/operations-backlog.md) и [пять фаз развития](docs/operations-plan.md) сохраняют историю этапов; реализованный P2 описан ниже, feedback и deployment readiness остаются отдельными задачами.

## Настоящие данные

Настоящих выгрузок в git нет: они содержат персональные данные. Получите их у владельца данных по согласованному каналу. Ожидается **12 исходных файлов: 8 CSV и 4 XLSX**, семь регионов; две части Павлодара находятся в отдельном подкаталоге. Точные имена и порядок сборки описаны в разделе 0 CLAUDE.md. Конвейер читает CSV; XLSX проверены как подмножества CSV, повторно их добавлять не нужно.

```bash
export NAZAR_SOURCE=real
unset NAZAR_WORK_DIR
export NAZAR_RAW_DIR=/absolute/path/to/authorized-export
.venv/bin/python -m src.dataset_manifest
# Просмотрите data/raw_candidate.json и подставьте напечатанный dataset_id:
.venv/bin/python -m src.dataset_manifest --accept ID
.venv/bin/nazar-build-data
.venv/bin/python train.py
.venv/bin/nazar-dashboard
```

Замените путь на свой каталог, сохранив имена файлов и устройство подкаталога Павлодара. Без `NAZAR_RAW_DIR` используется прежний каталог `drive-download-20260907T161509Z-1-001/` в корне проекта. Пути задаёт `src/paths.py`.

Manifest фиксирует версию всех 12 файлов, включая XLSX, которые не добавляются в канон повторно. Принятые версии лежат в `data/manifests/`, вне git. `python -m src.dataset_manifest --check` проверяет текущие байты; при изменении сырья сборка останавливается до адаптеров. Для новой выгрузки повторите создание, просмотр и явное принятие кандидата. Это не меняет эталон тем. Формат и границы — [CLAUDE.md, 0e](CLAUDE.md#0e-операционный-центр-109--границы-и-план-2026-09-27).

Для исходной выгрузки контрольный итог — **988 776 строк**: `problem` 658 103, `info` 308 305, `system` 22 368. Результаты: `data/unified.parquet`, `reports/metrics.json`, `reports/predictions.csv`, `models/model.pkl`. Для этой же выгрузки несовпадение эталона требует разбора. На новой выгрузке абсолютное число строк может измениться: сборка проверяет свойства разметки и новые категории, а не требует прежнего объёма.

## Как устроены данные

Семь регионов дают **шесть семейств схем**: названия полей, форматы дат и смысл полей различаются. Адаптеры приводят их к одной таблице, сохраняя источник и регион.

| Семейство | Особенность |
|---|---|
| Караганда | Тема в `sub_category`, сырая `category` обозначает службу; фактической даты закрытия нет |
| Костанай и Туркестан | Общая структура с уровнями услуг, датой закрытия и готовым признаком нарушения SLA |
| ВКО | Номер заявки, собственные справочники и дата закрытия |
| Алматы | Собственная схема; свободный текст из поля исполнителя в общую таблицу не переносится |
| Акмола | Тема в `direction`; даты закрытия плановые |
| Павлодар | Две CSV-части, справочники услуг и категорий; фактической даты закрытия нет |

Общая таблица содержит дату, регион, категорию и доступные поля района, исполнителя, статуса и SLA. Затем добавляются `topic` и `appeal_class`. Повреждённые строки со сдвигом полей отсеиваются, дубли обрабатываются по правилам семейства. Реальный свободный текст и примеры персональных данных здесь не публикуются.

## Что умеет система

| Возможность | Что делает и где граница |
|---|---|
| Классификация | Правила сопоставляют значения справочников с темой и классом. Пригодного корпуса реальных текстов заявителей в рабочих данных нет |
| Всплески | Показывает необычный рост жалоб относительно предыдущего окна; учитывает первый месяц и пропуски выгрузки. Не предсказывает аварию |
| Прогноз | Сравнивает простые недельные модели на достаточно длинных рядах; короткие и разорванные ряды исключаются |
| Риск просрочки | Только Караганда; ранжирование обращений. Порог 15 суток — допущение ТЗ, не норматив, а `updated_date` — прокси, не подтверждённая дата закрытия |
| NLQ | Детерминированный разбор вопросов к структурированной таблице; неподдерживаемые вопросы получают отказ. Это не поиск по свободному тексту |
| Dashboard | Восемь блоков Streamlit, фильтры, лента событий и очередь проверки риска |
| Excel/PDF | Агрегаты и лента при текущих фильтрах; блок риска не входит в экспорт. Для PDF нужны шрифт с кириллицей и браузер для графиков |

После сборки настоящих данных доступны команды:

```bash
.venv/bin/python -m src.spikes
.venv/bin/python -m src.forecast
.venv/bin/python -m src.nlq "сколько обращений было в прошлом месяце"
```

Fake-набор предназначен для сборки, риска и витрины. Прогноз, NLQ, проверка статуса 5o и сценарий `src.demo` не входят в его контракт.

## Проверки и CI

Workflow запускается при push в `main` и pull request. Все четыре job работают на Ubuntu 24.04. Зависимости устанавливаются из `requirements.lock` с проверкой хешей; проект — `--no-deps -e .`.

| Job | Что фактически проверяет |
|---|---|
| `linux-install` | Python 3.12, установка, импорты; без исходной выгрузки сборка объясняет отказ и возвращает код 2 |
| `docker-build` | Сборка образа по `Dockerfile` |
| `dashboard-smoke` | Запуск контейнера без данных, `/_stcore/health`, сообщение «Нет данных для витрины» в браузере без исключения |
| `fake-export` | Регенерация фикстуры, контрольные суммы, сборка, обучение, AppTest витрины, числовые эталоны, ПДн и отказ на новой info-категории |

Подтверждённый удалённый прогон четырёх job — [edb9a81, 27.09.2026](https://github.com/arlmango/NAZAR-109/actions/runs/36310639369). Последующие локальные изменения этим прогоном не покрываются. Тест после исправления внешнего каталога запускается локально так:

```bash
.venv/bin/python tests/test_fake_export.py
```

Тест по умолчанию использует внешний временный каталог результатов, не создаёт копию всего репозитория и проверяет неизменность `git status`. Сохранённый fake-отчёт проверяется чтением.

**Полный контейнерный прогон с данными, Excel и PDF с графиками ещё не проверен.** `fake-export` работает на Linux runner вне контейнера. CI не запускает Docker Compose. Инструкция контейнера и оставшиеся проверки — в разделе 0b CLAUDE.md.

## Персональные данные

Реальные сырые выгрузки, `data/`, `models/` и построчные артефакты, включая `reports/predictions.csv`, не коммитятся. В git допускаются код и проверенные агрегатные отчёты. Исключение для fake fixture и корпуса 5n обусловлено тем, что они синтетические и не описывают реальных людей.

В fake fixture специально заложены искусственные маркеры, чтобы проверка могла доказать, что обнаруживает телефоны, номера, адресные фрагменты и названия людей. Значения в README не приводятся. Готовые CSV, таблицы и экспорт проверяются сканерами `src/checks/pii_scan.py`, `src/checks/person_names.py` и `src/export.py`; одного чтения кода для приёмки недостаточно. Имена в названиях исполнителей маскируются при выводе. Шаблонные проверки имеют ограничения и не заменяют контроль свободного текста.

## Ограничения

- Нет входа, ролей, журнала действий и регулярного обновления данных. Витрина предназначена для внутренней сети.
- Регионы по-разному учитывают обращения; прямой рейтинг их объёмов некорректен. Поиск повторных обращений требует данных, которых в общей таблице нет.
- Сроки и риск не переносятся между регионами автоматически. Разметка SLA Костаная и Туркестана существенно различается и требует объяснения.
- Прогноз и детектор ограничены историческими окнами и качеством выгрузки; оценка риска не является откалиброванной вероятностью.
- Windows и полный контейнерный сценарий с данными пока не проверены. PDF без доступного браузера собирается без графиков с явным предупреждением.

## Experimental / R&D

Текстовые модели исследовались отдельно на внешних и синтетических корпусах, поскольку реальные тексты обращений недоступны из-за конфиденциальности. Эти модели не подключены к рабочей витрине, и их показатели не являются оценкой качества на реальных обращениях. **SYNTH — исследовательский корпус 5n; FAKE — сохранённая техническая fixture CI.** Код, отдельные команды, общие проверки ПДн и отчёты описаны в [навигаторе R&D](experiments/README.md).
